# Параллельное выполнение GoBadminton (parallel_v2), проект

Дата: 19.10.2026. Это только офлайн-проект: на сервере и в GitHub ничего не менялось.

## Коротко для Павла
- Несколько **слотов** (сначала 2), у каждого своя папка с кодом, своё состояние, своя блокировка, свой бюджет и своя QA. Общего checkpoint нет.
- Перед запуском технический PM строит **граф задач**. Задачи с разными файлами и областями идут параллельно. Задачи с пересечениями или зависимостями идут по очереди.
- Слияние в dev идёт **строго по одному** через очередь: rebase, полная QA, полный CI, fast-forward, DEV, приёмка.
- Модели подключаются через **адаптеры**. Сейчас включён только Codex. Cursor и Антигравити заведены, но выключены, и у каждого есть свои условия включения. Антигравити никогда не бывает QA, пока не исправлены 7 дефектов из #29.
- Переход без остановки трейна: #98 доходит до конца на старом исполнителе, а слоты включаются только после проверки изоляции и вашего «да».

## 1. Модель слота
| Ресурс | Путь / механизм |
|---|---|
| worktree | `/srv/gb-slots/<slot>/worktree` (отдельный `git worktree` или отдельный clone; общих каталогов нет) |
| state/checkpoint | `/var/lib/gobadminton-autonomy/slots/<slot>/checkpoint.json`, запись атомарная (tmp+rename) |
| блокировка слота | `flock` на `/run/gb-slots/<slot>.lock`: один процесс на слот |
| бюджет | `/var/lib/.../slots/<slot>/budget.json`: попытки ≤3, токены/вызовы на модель, wall-clock |
| QA-сессия | отдельные CODEX_HOME/tmp на слот, QA всегда через новую ephemeral-сессию на точном SHA |
| процесс | systemd-шаблон `gobadminton-slot@<slot>.service` (свой User, `StateDirectory=`, `PrivateTmp=yes`, `ReadWritePaths=` только свои каталоги), `gobadminton-supervisor.service` планирует задачи и владеет очередью слияния |

Инвариант: ни один путь слота A не лежит внутри путей слота B. Unit слота A не может писать в каталоги B, это обеспечивает `ReadWritePaths`.

## 2. Реестр блокировок ресурсов
- В задаче при публикации объявлены `areas` (иерархия `web:games:map`) и `globs` (пути).
- Конфликтуют: одинаковые или вложенные области (родитель и ребёнок), пересекающиеся глобы, а также `global` с чем угодно.
- Всегда в одиночку: `global, migrations, packages/contracts, workflows, scripts/chatops`. Задача без объявленных areas/globs тоже считается одиночной.
- Аренда (lease) — это файл, который держит `flock` живого процесса слота. Если процесс падает, ядро снимает flock, и следующий захват удаляет устаревшую аренду (crash-safe). Ручных сбросов не бывает.
- **Integration mutex** — один на всю систему, его держит только текущий интегратор.

## 3. Граф PM и планировщик
- Узлы — задачи, рёбра — `depends_on` плюс конфликты блокировок (конфликтующие пары упорядочиваются по приоритету).
- Задача готова, когда все зависимости `done`. Если зависимость `parked`, зависящие задачи ждут задачу на замену.
- Свободный слот берёт первую готовую задачу, у которой адаптер включён для роли author и блокировки захватываются без конфликтов.
- Параллельно идут не больше N слотов и не больше 2 CI одновременно.
- Модель для задачи выбирает PM по таблице «клиент / точный ID модели / уровень рассуждения / квота / цена». Без подтверждённой модели задача не планируется.

## 4. Интерфейс адаптера модели
У каждого адаптера отдельные состояния: `installed`, `in_catalog`, `authenticated`, `inference_proven`, `owner_approved`, `quota_remaining`, а также роли (`author|qa|review`). Адаптер включён для роли, только если все состояния истинны и квота известна и больше 0.
- **codex** (0.160.1): author, qa, review. Сейчас единственный, кто включён.
- **cursor-agent**: только author, выключен (нет токенов). Условия включения: новый расчётный период, Auto mode, provider-тест (3 эталонные задачи в песочнице, точный ID модели в логе), «да» Павла.
- **agy** 1.4.2: только review, выключен. Роль QA запрещена в коде, пока не закрыт #29. Условия включения: 7 дефектов исправлены, provider-тест, «да» Павла.

## 5. Бюджеты и квоты
- `UNKNOWN ≠ 0`. Неизвестная квота не значит «бесплатно» и не значит «пусто»: адаптер с UNKNOWN не планируется автоматически, нужно измерение или явная настройка лимита от Павла.
- На слот: ≤3 попытки, лимит вызовов модели, wall-clock. На провайдера: дневной лимит. Превышение лимита ведёт к park, а не к ожиданию бесконечно.

## 6. Очередь слияния (по одному)
Для каждого кандидата под integration mutex: rebase на текущий dev → **полная независимая QA на новом SHA** → **полный CI** → проверка, что dev не сдвинулся → ff → деплой DEV → приёмка → освобождение блокировок. Если что-то упало, кандидат возвращается в свой слот (это расходует попытку), а очередь идёт дальше.

## 7. Сбой, park и замена (на слот)
- Сбой QA или CI: новая попытка в том же слоте, всего ≤3.
- После 3 попыток: PARK_V1, блокировки освобождаются, слот свободен. Технический PM (цикл successor_loop) собирает все отчёты QA, пишет задачу на замену, ревьюер её проверяет, потом она публикуется. Зависимые задачи ждут.
- Сбой процесса слота: systemd перезапускает его, checkpoint берётся из собственного state, блокировки уже сняты ядром или снова захватываются тем же слотом.
