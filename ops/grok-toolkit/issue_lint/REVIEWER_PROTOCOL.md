# REVIEWER_PROTOCOL — независимая проверка тела Issue перед публикацией

Запускается перед КАЖДОЙ публикацией Issue `GOBADMINTON_AUTONOMY_V1`.
Ревьюер — отдельный субагент, **не автор тела**. Он только читает: ничего не публикует,
не правит тело, не трогает репозиторий. Токен GitHub не печатать.

## Вход
- путь к файлу тела (`*.body.txt`);
- вывод `python3 lint_issue.py <тело>` (если есть FAIL, ревьюер всё равно проверяет и даёт NELZYA);
- история: номера и причины провала предыдущих попыток этой задачи (для преемника).
- **для преемника обязательно**: полный текст замечаний независимой QA всех прошлых попыток
  (`qa-<issue>-a<k>.json` исполнителя, `/home/__EXEC_USER__/.gb-autonomy-state/`, только чтение),
  собранный в `qa_history_*.json`. Для codex-review он приклеивается к staged-файлу приложением:
  `python3 make_review_input.py BODY.txt qa_history.json OUT.txt --issues N` (обёртку не менять).

## Чек-лист (каждый пункт: ДА / НЕТ / НЕТ ДАННЫХ + цитата из тела)
1. **Нет условий остановки.** Нет «если … нет/не влито/не совпало — остановись / stop and say / abort / BLOCKED». Есть явное «NEVER stop … no stop conditions».
2. **Песочница автора.** Нет шагов с сетью и записью git-метаданных: fetch, pull, clone, ls-remote, push, checkout/switch/reset/stash, сравнение с origin/dev, npm/pnpm install. Допустимо только чтение: `git show`, `git cat-file`, `git diff`, `git log`.
3. **Проверка истории провала (правило оунера 19.10.2026).** Если это преемник: в теле есть раздел
   «Замечания QA предыдущих попыток», где КАЖДОЕ замечание QA каждой прошлой попытки перечислено как
   `#N aK sha8: замечание -> как учтено (пункт acceptance)` или `-> вне scope: причина`; способ учёта реально
   закрыт acceptance; названа реальная причина провала, и той же конструкции в новом тексте нет.
   Пропущенное замечание или пункт без «->» = НЕТ. Линтер проверяет это правилом [Q] (FAIL без раздела).
4. **Нет противоречий.** Не запрещены тесты и одновременно требуются; «после приёмки X» и «текущий HEAD» одновременно; «не трогать А» и А в allowed_paths.
5. **Обязательные тесты и запасной путь.** Тесты названы обязательными и должны быть в diff; есть «NOT_TESTED с точной причиной вместо остановки, код и тесты остаются в diff»; есть «handoff-only diff = FAIL».
6. **Проверяемость acceptance.** Каждый пункт можно проверить по diff или выводу команды без догадок; нет критериев, зависящих от удалённого состояния, устройства или чужой задачи; пунктов не больше 9.
7. **allowed_paths.** Узкие файлы, не `apps/**` и не `apps/web/**`; нет API, контрактов, миграций, зависимостей, workflows, control-документов; число записей разумно (≤14); есть `docs/handoffs/**`.
8. **Ссылки существуют.** Каждый упомянутый путь есть в текущем dev или явно помечен «создать»; источники-коммиты существуют; ссылка на документ, которого нет, не стоит на критическом пути.
9. **База.** Названный dev/base SHA равен текущему HEAD dev на момент публикации (`git ls-remote` НЕ нужен, линтер берёт SHA через GitHub); в тексте нет «если база изменилась — стоп», только «слей вручную».
10. **Размер.** Одна задача = один независимый набор файлов и одна приёмка; goal ≤ 5000 знаков, acceptance ≤ 3500, иначе резать.
11. **Совпадение с макетом и решением оунера.** Тело не противоречит последнему решению оунера и макету (если задача визуальная, ссылка на эталон есть).
12. **Ясность для автора, который не видит чата.** Нет ссылок на «как в прошлый раз», на разговор, на «см. выше»; все термины и номера задач расшифрованы одной фразой.

## Правило решения
- **NELZYA**, если хотя бы один из пунктов 1–5, 7–9 = НЕТ, или линтер дал FAIL, который ревьюер не опроверг письменно.
- **MOZHNO** только когда пункты 1–5, 7–9 = ДА, остальные ДА или осознанно принятые WARN (перечислить).
- «НЕТ ДАННЫХ» по пунктам 8–9 (GitHub недоступен) = NELZYA до повторной проверки.
- Ревьюер не исправляет сам: возвращает список правок автору тела, после правок проверка идёт заново, другим ревьюером или тем же, но с чистого листа.

## Шаблон вердикта
```
ВЕРДИКТ: MOZHNO | NELZYA
Тело: <файл>, sha256 <первые 12 знаков>
HEAD dev на момент проверки: <sha8>
Линтер: PASS/WARN/FAIL (FAIL: n, WARN: n)
Пункты 1–12: 1 ДА | 2 ДА | 3 НЕТ — «цитата» | ...
Причины (если NELZYA):
 1. <пункт, цитата, что исправить>
Принятые WARN (если MOZHNO):
 - <код, почему допустимо>
Что изменилось бы вердикт: <кратко>
Ревьюер: <идентификатор субагента>, автор тела: <идентификатор>  (должны отличаться)
```

## Порядок перед публикацией
1. `python3 lint_issue.py BODY.txt` → нет FAIL.
2. Субагент-ревьюер заполняет шаблон вердикта.
3. Публикуем только при MOZHNO; текст вердикта сохраняем рядом с телом (`BODY.verdict.md`).
4. После публикации, если dev ушёл вперёд до того, как задачу взял исполнитель, повторить шаг 1 (пункт 9).
