## 2. Текущие ограничения и почему один слот

Из кода (факты):
- `state.json` = `{active, done}`: одно поле `active`. `Store.claim()` возвращает существующий `active`, пока его фаза не `done`. `parked.json` отдельный файл (`{parked: [...]}`), `state.json` его схему не знает.
- `main()` ведёт цикл по одной задаче; блокированная задача `blocked` держит слот (park v2 теперь освобождает).
- Один блокирующий lock-файл `worker.lock` на каталог состояния, одна systemd-служба `gobadminton-autonomy` (проверка `MainPID`, `KillMode=control-group`, пользователь `__EXEC_USER__`).
- Рабочее дерево `worktrees_root/issue-N`, ветка `automation/issue-N`, QA в `qa-issue-N-aM`: имена уже по номеру задачи, то есть **изоляция по задачам уже есть**.
- Слив: `execute()` проверяет `remote_dev() == active['base']` (отказ «dev baseline drift»), `merge-base == base` («not a fast-forward»), затем `git push --atomic … head:refs/heads/dev`. Это и есть причина строгой последовательности: база каждой задачи = `dev` на момент старта, значит вторая задача после слива первой отклонится.
- CI запускается пушем ветки `automation/issue-N` (`Product CI`, 7 заданий: `foundation, source (api), source (web), source (admin), source (contracts), database, receiver`), после слива пуш в `dev` запускает `DEV deploy` (`checks, images, deploy`; шаг «Apply, browser-smoke, accept; rollback on failure»). Затем читается серверный ACCEPTED `r<run>-a<attempt>` с совпадением SHA и `/v1/meta gitSha`.
- Право Owner: `OWNER_ID`, `approved_since`, неизменённый Issue (`unchanged_issue`).

Зачем один слот: (1) защита `dev` от конфликтов и гонок деплоя, (2) QA и CI привязаны к точному SHA на точной базе, (3) один DEV-стенд: приёмка по `release_id` однозначна только если деплоев не два одновременно, (4) простота восстановления: одна `active` и один checkpoint. Это инженерные причины, не Owner-решение.

## 3. Целевая картина (кратко)

```
claim (N=2) -> слот A: автор+PR-ветка+QA+CI (параллельно) \
                                                           -> ОЧЕРЕДЬ СЛИВА (по одному) -> push dev -> DEV deploy -> ACCEPTED -> следующий
claim (N=2) -> слот B: автор+PR-ветка+QA+CI (параллельно) /
```
Параллельно только «длинная» часть (автор, QA-модель, CI на ветке). Короткая критическая часть (рассматриваемая база, fast-forward, деплой, приёмка) идёт строго по одной задаче через единую дорожку слива.

## 4. Целевая конструкция

### 4.1 Схема состояния и миграция
Сохраняем `state.json` совместимым: **ничего не ломаем, а добавляем рядом**.
- `state.json` остаётся `{active, done}`. `active` по-прежнему допустимо, это «слот 0» и единственный ключ при выключенном флаге. Старый код и мои скрипты чтения продолжают работать.
- Новый файл `slots.json` (отдельно, по образцу `parked.json`): `{schema:1, max_slots:2, slots:{"1": <active-подобная запись или null>}, merge_lane:{holder: issue|null, since, base}}`. Запись слота = тот же объект, что `active` сейчас (issue, task, phase, base, head, pr, ci, qa, attempt …) плюс `slot`, `claimed_at`, `scope` (вычисленное множество путей и locks).
- Инвариант: каждая задача лежит ровно в одном месте: `active`, `slots.*`, `done` или `parked`. При включённом флаге `active` = слот 0, слоты 1..N-1 в `slots.json`.
- Миграция: при первом запуске с флагом создаётся `slots.json` пустым (бэкап `state.json` и `parked.json` под именем `before-multislot-<ts>.json`, без перезаписи). Откат = удалить флаг и `slots.json` игнорируется; пока в слотах 1.. нет задач, состояние идентично старому.
- Фазы без изменений (`PHASES`) и добавляется одна: `merge_wait` (QA и CI зелёные, ждёт очередь слива). Для старой версии кода неизвестная фаза = отказ запуска («unknown phase»), поэтому откат обязан сначала опустошить слоты (см. раздел 8).
- Запись `done` (список номеров) общая; вывод в monitor получает поле `slots`.

### 4.2 Граф и пересечение файлов
Для задачи вычисляется `scope`:
1. **Объявленное**: новые необязательные поля задачи `depends_on` (список номеров Issue, до 8, по образцу `depends_on_completed/accepted` старого Runner) и `locks` (по образцу старого Runner: `web:games`, `api:profiles`, `map-assets`, `schema-contracts`, `deploy-runtime`, `global`). Валидатор расширяется явно (сейчас набор полей закрыт); задачи старого формата остаются валидными и получают `locks=["global"]`, то есть **без объявления слоты не используются**.
2. **Вычисляемое**: множество `allowed_paths` (шаблоны `prefix/**` и точные). Два шаблона пересекаются, если один путь является префиксом другого. Дополнительно «горячие файлы» (всегда общие): `pnpm-lock.yaml`, `package.json`, `packages/contracts/**`, `apps/api/migrations/**`, `.github/**` и все пути из `docs/**`, которые трогают оба. Любая задача с миграцией БД или общими контрактами = `global` (идёт одна).
3. **Решение**: задачи несовместимы, если выполняется любое из: пересечение путей; конфликт locks; одна зависит от другой (`depends_on` не `done`); у кандидата `global`; у кандидата нет объявления. Ошибка в сторону запрета.
4. Граф хранится как зафиксированные записи в самой задаче и в `slots.json` (причина отказа записывается, как «wait reason» в старом Runner), а не вычисляется LLM. Технический PM (этап по спеке) может только **предложить** `depends_on/locks`; обычный код проверяет и ужесточает, никогда не ослабляет.
5. Компактная «капсула задачи» для PM по образцу `compact_task_capsule.py`: зависимости и их статус, locks, пересекающиеся активные, SHA базы и admission, `evidence_fingerprint`; без нового события LLM не вызывается.

Что не меняется в `claim`: порядок по времени и номеру; Issue всё ещё должен быть Owner-авторизован. Новое: после выбора первой задачи claim смотрит следующую по порядку и берёт её во второй слот только при полной совместимости и при условии «слот 1 в фазах автора/QA/CI, но не в слиянии».

### 4.3 Слоты, ветки и рабочие деревья
N=2 на первом этапе (конфигурация `max_slots`, жёсткий потолок в коде 2 до решения Owner).
- Рабочее дерево и ветка уже по задаче (`issue-N`, `automation/issue-N`), QA-дерево `qa-issue-N-aM`. Добавляется проверка занятости пути между слотами.
- Каждому слоту отдельный подпроцесс/поток исполнения внутри той же службы (одна служба, одна `worker.lock`; не второй оркестратор). Рекомендация: потоки с общей блокировкой записи `state` (сериализованный `save()`, одна atomic-запись), либо лёгкие дочерние процессы под одним `control-group`. Выбор: **потоки + одна блокировка**, потому что `Store` и `worker.lock` остаются единым владельцем и сигнал SIGTERM обрабатывается одним местом.
- Песочница, права, Landlock, `permission_config` не меняются: у каждого запуска своя рабочая директория и свой набор «writable». Один слот не видит дерево другого (проверить, что `writable` не включает соседний `issue-M`).
- Квота моделей/API: пул один; слот 2 стартует только при свободной квоте, при `QuotaWait` слот ждёт, `max_attempts` не обходится.

### 4.4 Что остаётся строго последовательным
1. **Дорожка слива** (`merge_lane`): ровно один держатель. Входит задача в `merge_wait`, берёт замок, делает: проверка базы → при необходимости перебазирование/повторная проверка (раздел 5) → `push --atomic head:dev` → ожидание `DEV deploy` → серверный ACCEPTED + live SHA → отпускает замок и пишет `done`. Следующая задача входит в дорожку только после ACCEPTED предыдущей. Это сохраняет «DEV deploy ACCEPTED на каждый слив».
2. Запись в `dev`, DEV-деплой, откат деплоя: только по одному.
3. Любая задача `global`, ops-изменения самого исполнителя (`scripts/chatops/**`, workflows), миграции БД, смена контрактов: идут одни, пока другой слот пуст («дренаж»).
4. Park/Resume/Recovery операции Owner: только над одним слотом за раз, по существующим маркерам с проверкой `issue`, `head`, `attempt`.
5. Установка и откат самого механизма.

## 5. Режимы отказа и правила

| Риск | Правило |
|---|---|
| Конфликт после слива первой | Вторая задача проверяется на устаревшую базу. Если `dev` ушёл вперёд, а пути не пересекаются, **перебазирование без изменения содержимого** (`git rebase`/cherry-pick на новый `dev`) допускается только если дерево, затронутое задачей, совпадает по diff (идентичный патч, проверка `git range-diff`/`patch-id`). Иначе кандидат получает новый SHA, и **вся приёмка повторяется на новом SHA**: новая независимая QA точного SHA, полный CI из 7 заданий. Старая QA не переносится: «exact SHA» не нарушается. |
| QA на устаревшей базе | Правило для проекта: QA и CI привязаны к SHA и базе; если база сменилась до слива, QA-PASS не считается действительным для нового SHA, а для того же SHA (без перебазирования) fast-forward невозможен, значит всё равно нужен новый SHA. Поэтому реальный выбор только один: перебазировать и повторить QA+CI. Сокращённая повторная QA (дельта) допустима **только если Owner отдельно разрешит** (есть `OWNER_DECISION_DELTA_BASED_VERIFICATION_V001.md`, не читал; применимость надо подтвердить). |
| Авто-перебазирование ломает тесты | Задача возвращается в слот на попытку (учитывается в `max_attempts`) либо паркуется; «silent merge» нет. |
| Минуты CI | Два слота = до двух одновременных `Product CI` плюс `DEV deploy`. Повторная проверка после перебазирования добавляет третий и четвёртый прогон. Меры: при N=2 максимум по одному CI на слот; лимит повторных CI на задачу = 1 сверх обычных; метрика расхода минут в отчёте. Оценка: до +60–80 % минут на пару задач в худшем случае. Цифры CI в минутах нужно снять с реальных запусков (не измерял). |
| Гонки деплоя | Замок дорожки слива и проверка `remote_dev()` под замком; `release_id` сверяется как сейчас. Два деплоя одновременно невозможны по конструкции; дополнительно запрет push в `dev` при незавершённом `DEV deploy`. |
| Падение процесса по слотам | Для каждого слота своя запись фазы; recovery идёт по каждому слоту отдельно по существующим правилам (`candidate/pr_wait/ci/promoting/dev_wait` можно восстановить, «interrupted writer/claim/reviewer» = ручная сверка). Замок слива после падения: держатель определяется по `dev`: если `dev == head` задачи, продолжаем с `dev_wait`; если `dev == base`, замок освобождается. Двойной держатель = блокировка обоих. |
| Слот без `merge_wait` блокирует | Слот A в слиянии, слот B ждёт в `merge_wait`: тайм-аут и размер очереди ограничены; B не освобождается автоматически, но не мешает. |
| Одна зависает, вторая нет | Блокированный слот не держит дорожку слива; park v2 освобождает слот; слот B продолжает. |
| Взаимные зависимости, обход проверки | `depends_on` на не done = отказ claim; циклов нет (проверка графа). Ложный `depends_on` может только замедлить, не ослабить. |
| Загрязнение общего состояния | Один `save()` на все слоты под замком; один `atomic()`; порядок записи: сначала `slots.json`, потом `state.json` (как `park`), идемпотентно после падения. |
| Монитор и OPS | Монитор (ops-monitor) должен показывать слоты, иначе «active» вводит в заблуждение; доработка схемы статуса, безопасная команда статуса с проверкой версии схемы. |
| Двойной механизм | Старый Runner не должен писать в `dev` одновременно; подтвердить статус (пробел 6). |

## 6. Поэтапное внедрение

**Этап 0. Карта зависимостей, только чтение (0,5–1 день).** Сверить установленную копию исполнителя с `dev` (хеш). Выяснить статус старого Runner. Собрать для открытых/планируемых задач (#68…#88, M0b–M7, T0a, P-пакетная загрузка фото, PM-распределение) таблицу `depends_on`, `locks`, `allowed_paths` и показать, какие пары могли бы идти параллельно. Выход: файл карты (в GitHub как документ, по решению Owner) и показ Owner. Ничего не запускается.

**Этап 1. Два слота, холостой прогон (3–5 дней разработки).** Код под флагом (по умолчанию выключен): расширение валидатора (`depends_on`, `locks`), вычисление `scope`, `slots.json`, дорожка слива, но запись в `dev` и в слоты запрещена; режим `dry-run` только логирует «взял бы слот 2: задача X, совместима с Y» и «слив пошёл бы в таком порядке». Тесты: юнит (пересечение путей, locks, миграция, recovery), имитация гонок, воспроизведение сценариев из старых тестов (`test_four_compatible…`, `test_broad_claim_blocks…`). Независимая QA точного SHA, CI 7 заданий, PR в `dev` по обычному пути OPS (так же как RESUME_V1/PARK_V2).

**Этап 2. Боевой режим с флагом (1–2 дня установки + наблюдение).** Установка по процедуре RESUME_V1: бэкап адаптера и каталога состояния, хеши, перезапуск службы, Owner GO. Флаг `multislot=on`, `max_slots=2`. Первые две реальные пары: **две заведомо несвязанные малые задачи** (например, документ плюс отдельный компонент). Условие выхода: две задачи слиты по очереди, обе DEV ACCEPTED, версии на DEV совпали, откат отрепетирован. Затем неделя наблюдения; только после неё обсуждается N=3.

## 7. Обязательная независимая проверка и доказательства на DEV
- Независимая QA точного SHA механизма (автор не принимает собственную работу), полный CI из 7 заданий.
- Негативные тесты: пересечение путей не даёт слот; задача без объявления идёт одна; `depends_on` на незавершённую блокирует; циклы отвергаются; `global` дренирует слоты; PROD/PLAN/VPN пути отклоняются как сейчас (`safe_path`); два одновременных push в `dev` невозможны; падение на каждой границе фаз и в замке слива восстанавливается без двойного деплоя; устаревший SHA не принимает старую QA.
- Живое доказательство на DEV: две реальные несвязанные задачи, у каждой свой PR, QA по SHA, CI 7/7; слив строго по очереди (SHA слива и ACCEPTED `release_id` по каждой в логе), live `/v1/meta gitSha` равен второй; репетиция отката: флаг выкл. с одним слотом в полёте, дренаж без потерь; проверка, что `state.json` читается старым кодом.
- Живой рычаг расхода: учёт CI-минут и вызовов модели с честным UNKNOWN (как требует спека PM).
- UAT, если применимо к пользовательским задачам, отдельно от CI.

## 8. Откат
1. Флаг `multislot=off`: новые слоты не берутся; слот 1 дорабатывает до `done`/`parked` (дренаж), затем можно перезапустить службу.
2. Если нужно срочно: пауза claim (нет новых), дождаться пустых слотов 1.., пустой `merge_lane`; при зависании использовать park v2/resume (Owner-комментарий), не правку state.json руками.
3. Файловый откат: вернуть сохранённые адаптер и `before-multislot-<ts>.json`, удалить `slots.json` только при пустых слотах, перезапустить службу. Старый код не знает фазу `merge_wait`, поэтому до отката ни один слот не должен в ней находиться.
4. Деплой на `dev` откатывается существующим механизмом `rollback on failure`; ручной откат коммита на `dev` отдельная процедура PM (не автоматическая).
5. Откат не трогает PROD/PLAN/VPN, потому что механизм их не касается.

## 9. Оценка трудозатрат
| Этап | Работа | Оценка |
|---|---|---|
| 0 | сверка, карта, показ | 0,5–1 дня |
| 1 | код (схема, валидатор, scope, слоты, дорожка слива, recovery) около 600–900 строк плюс тесты 1000+ | 3–5 дней, плюс 1–2 дня независимая QA и исправления |
| 2 | установка, живая пара, наблюдение | 1–2 дня плюс неделя наблюдения |
Итого 6–9 рабочих дней активной работы и неделя наблюдения. Риски графика: ёмкость слота исполнителя (сейчас занят карточными задачами), две-три итерации QA (как у #66/#68), согласование с работой PM-маршрутизации (та же область кода: порядок, чтобы не править `autonomous_issues.py` двумя PR сразу; лучше PM-маршрутизацию делать первой, а multislot поверх).

## 10. Решения Owner, которые нужны
1. **Формулировка правила**: заменить «один писатель» на «один писатель на независимый набор файлов; запись в `dev`, DEV-деплой и приёмка строго по одному». Предлагаемый текст: *«Исполнитель может вести до двух задач параллельно, если у них нет общих файлов, общих областей (locks) и зависимостей. В `dev` задачи сливаются по одной, каждая со своей независимой QA точного SHA, полным CI и приёмкой DEV ACCEPTED.»* Да/нет.
2. N=2 на старте, потолок 2, рост только отдельным решением. Да/нет.
3. После слива первой кандидат второй перебазируется и проходит **полную** QA+CI заново (рекомендую). Или разрешить сокращённую дельта-проверку (рискованнее). Выбор.
4. Кто объявляет `depends_on`/`locks`: Owner в Issue, PM как предложение с проверкой кодом, или оба. Рекомендую: PM предлагает, код проверяет, любая задача без объявления идёт одна.
5. Какие области всегда `global` (рекомендую: миграции БД, `packages/contracts`, workflows, `scripts/chatops`, lock-файлы).
6. Бюджет CI-минут: допустимый рост (до +80 % в худшем случае) и лимит одного повторного CI на задачу.
7. Разрешение на ops-установку тем же путём (бэкап, GO, `sudo`-действие), отдельным Owner GO.
8. Порядок: сначала PM-маршрутизация (спека), затем multislot, или наоборот. Рекомендую PM первым.
9. Подтвердить статус старого Runner в `_automation/…` (выведен ли из работы), чтобы два механизма не писали в `dev`.
