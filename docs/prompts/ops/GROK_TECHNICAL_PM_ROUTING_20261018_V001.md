## 1. Цель поручения

Реализовать следующий процесс в существующей инфраструктуре GoBadminton:

**Owner → Grok OPS → технический PM на немецкой VPS → проверка плана обычным кодом → существующий исполнитель с явно выбранной моделью → независимая QA → GitHub Actions → DEV.**

Нужен не очередной аналитический отчёт, а работающий ограниченный V1. После согласования задачи и архитектуры Owner не должен самостоятельно выбирать CLI, модель, reasoning effort или переносить поручения между агентами.

Grok остаётся единственным пользовательским OPS-координатором. Отдельная сильная модель на VPS разбирается в задаче и готовит технический план. Обычный программный исполнитель проверяет этот план и выполняет только разрешённые действия.

Это расширение существующего delivery-контура, а не новый оркестратор, сервер, task tracker или автономная команда ботов. Не переписывать приложение или архитектуру продукта ради инструмента управления.

## 5. Технический PM на VPS

Сделать ограниченный read-only planning stage в существующем execution-контуре. Начальный кандидат на профиль PM — доступный сильный Sol High либо подтверждённый сопоставимый профиль. Не использовать extra-high для всего по умолчанию. Более глубокий режим применять только к определённой технической неоднозначности/риску в рамках настроенной policy.

PM должен изучить принятую задачу и архитектуру, относящиеся к ним код, API-контракты, зависимости и критерии приёмки. Ему недостаточно классифицировать заголовок или ключевые слова. Слово «privacy» само по себе не означает самый дорогой профиль; слово «UI» не делает изменение разрешений безопасной рутиной.

Его вход: точная версия поручения и её authority reference, базовый SHA, релевантная принятая архитектура, относящиеся Owner-уточнения, необходимые части кода/контрактов/Style Guide, подтверждённые зависимости, реестр профилей и бюджетная policy.

Контекст получать адресно из GitHub и разрешённых source snapshots. Не загружать весь репозиторий, все журналы, всю историю чатов и прежних ошибок в каждый вызов. Общий проектный индекс и исходники доступны для адресного чтения; сводка не заменяет критический первоисточник. Не предоставлять PM секреты и необработанный приватный checkpoint.

PM определяет, что уже реализовано, что реально требуется изменить, нужно ли разбиение, порядок этапов, риски, автора, независимого проверяющего и критерии. Утверждённую архитектуру не проектировать заново. Новое противоречие оформить конкретным blocking decision только для зависимого участка.

Модель-планировщик не пишет product source, не меняет доверенную policy, не запускает других агентов, не принимает свою же работу и не получает root/GitHub-write credentials. Инструменты чтения и вывод результата ограничены; инструкции из Issue, исходников и логов рассматриваются как недоверенные данные.

## 6. Машиночитаемый план и проверка перед запуском

PM возвращает короткое объяснение плюс JSON по версионированной схеме. План хранится как неизменяемый артефакт, а не только текст в чате.

Минимальное содержание:

| Поле | Смысл |
|---|---|
| Task binding | Issue, версия/хеш исходного поручения, authority reference, base SHA, версия routing policy. |
| Sources | Точные ревизии использованных спецификаций и критических входов. |
| Readiness | Готовность, зависимости с доказательствами, конкретные blockers. |
| Steps | Минимально необходимое число последовательных этапов, результаты и зависимости. Одна цельная задача может остаться одним этапом. |
| Assignments | Для каждого этапа роль, допущенный CLI/model/effort, reason и разрешённые paths/tools. |
| QA | Отдельный профиль QA, exact-candidate requirement и обязательные проверки. |
| Budget | Пределы вызовов, попыток, времени, доступного расхода; условия допустимого fallback и перепланирования. |
| State | План готов / заблокирован с причиной; неопределённость и не подтверждённые данные явно видны. |

Обычный код, а не модель, проверяет schema, размеры, authority, точный task/base binding, зависимости, допустимые profiles/effort, лимиты и границы paths/tools. Независимые обязательные safety-правила имеют приоритет над модельной оценкой риска.

Никакого `eval`, исполнения произвольных shell-команд из JSON или передачи выданных моделью аргументов напрямую в privileged launcher. Запуски строятся из доверенного реестра и валидированных значений.

План НЕ является новым разрешением. Каждый внутренний этап наследует полномочия родительской Owner-approved задачи и может только сужать scope. Не нужно требовать Owner-комментарий для каждого внутреннего шага, но нельзя подделывать Owner identity или удалять существующую проверку допуска. При необходимости оформить совместимый parent-plan binding в рамках этой OPS-доработки и проверить его отдельно.

В V1 не создавать новый distributed scheduler: минимальный последовательный план выполняется тем же единственным executor. Не менять приоритет задачи только потому, что она дешевле или удобнее для теста.

## 7. Политика выбора моделей и экономия

Экономичность оценивается по ресурсу на принятую задачу, а не по минимальной цене одного вызова.

Рутинная работа с однозначным проверенным шаблоном может использовать готовый маршрут без глубокого перепланирования. Нетривиальная разработка, состояния, интеграции и медиа получают подходящий сильный профиль. Новая неоднозначная безопасность/права/приватность требуют чувствительного технического профиля и соответствующей независимой проверки.

Шаблонный маршрут разрешён только для явно перечисленных и проверяемых случаев. Не пропускать анализ произвольного задания потому, что текст содержит «простая правка».

PM выбирает модель по сложности, риску, необходимым инструментам, подтверждённой пригодности, доступности и квоте. Известная низкая цена не компенсирует недостаточную способность выполнять задачу. Не навязывать разных провайдеров ради самого количества агентов.

Профиль QA выбирается отдельно от автора. Минимум — новая изолированная read-only QA-сессия, exact SHA и неизменность source. Другой провайдер не заменяет изоляцию, а тот же провайдер не отменяет независимость сессии. Для чувствительной работы применять действующие дополнительные требования.

QA FAIL и красный CI не включают автоматический переход на дорогую модель. Сначала различить source defect, проблему тестовой среды, quota, unavailable access, неверный baseline и новый scope. Смена модели не обходит max_attempts и не стирает FAIL.

Неизвестный/недоступный профиль не заменять молча default-моделью. Использовать только заранее допущенный fallback с достаточными правами и качеством; иначе сохранять состояние и выдавать точный blocker. При незавершённом старом запуске сначала установить его outcome и освободить владение штатно, затем запускать замену.

Статусы, CI polling, проверка SHA, таймеры, сборка и обычная публикация выполняются кодом без дополнительной LLM-координации на каждый шаг. У Grok должны быть события и компактный проверенный статус, а не дорогой повторный разбор всей истории.

## 8. Учёт использования и бюджетные границы

Собирать на каждый реальный вызов: task/plan/step/attempt, роль, фактически выбранные CLI/model/effort, время, outcome, доступные input/cached/output/reasoning tokens, источник метрик, известный вид биллинга и оценку стоимости только при проверяемых исходных данных.

Provider-specific показатели нормализовать осторожно: не суммировать reasoning/cached tokens повторно, если они уже входят в другую категорию. Не публиковать сырые transcripts и персональные данные ради отчёта.

Отдельно учитывать расход модели PM, автора, QA, повторов и Grok-управления — последнего только когда его метрики реально доступны. Траты GitHub Actions и серверные ресурсы не смешивать с LLM-токенами.

Различать включённую подписочную квоту и дополнительные деньги. Наличие оплаченной подписки не означает безлимит. Не включать Cursor on-demand, новый платный API, новую подписку или автопополнение. Применять имеющиеся разрешённые подписки и существующие пределы.

Если точная стоимость, остаток квоты или историческая статистика недоступны — писать `UNKNOWN/NOT_AVAILABLE`, не ноль. Отсутствие полной долларовой статистики не должно блокировать V1 с консервативными лимитами вызовов, времени и повторов, но нельзя заявлять гарантированный денежный потолок, который технически не обеспечен.

Один план на одну неизменную версию задачи. Перед повторным использованием проверить релевантность base/входов и зависимости. При существенном drift или изменении scope — новая версия плана, а не тихое применение устаревшего. Не перепланировать при каждом poll. Повторное планирование имеет явный предел в policy; бесконечные циклы «план → проверка плана → перепланирование» запрещены.

Исполнитель принудительно контролирует то, что возможно: допустимый профиль, количество запусков/попыток, timeout, плановый лимит контекста, provider quota/backoff и поддерживаемые API-ограничения. Не выдавать timeout за точный hard token cap. PM/Grok не могут сами увеличить лимит при достижении потолка.

## 9. Сохранение существующего процесса

Сохранять single-writer, task worktrees, sandbox, historical FAIL, независимую QA, полные CI-гейты, exact SHA, серверный ACCEPTED, проверку live версии и rollback. Существующий SMTP-watchdog не заменять модельным наблюдением.

Активные задачи не перепланировать и не мигрировать молча. Первичное включение — на безопасной границе для новых допущенных задач. Старый workflow должен продолжить читать свои checkpoint либо иметь проверенную совместимую миграцию и откат без повторного исполнения.

Планирование, публикация плана и запуск этапа должны иметь устойчивый идентификатор и запись состояния. Повторное событие или restart не должны запускать повторного платного PM/автора поверх уже начатого и не должны терять исходный результат. Не обещать exactly-once; сделать явное reconciliation для неизвестного исхода.

История фаз и счётчики должны сохраняться при смене моделей, исправлениях и возврате на старую версию runtime. Откат до несовместимого schema после новых записей проверяется отдельно; восстановление старого backup не должно стирать новые завершённые задачи.

Доступ Grok по `grokops` не равен полномочиям самого executor. Предусмотреть в существующем безопасном статусе сведения о планировании, выбранном исполнителе и бюджете. Не выдавать ради этого private state, credential store или неограниченный sudo.

## 10. Порядок реализации и допуска

**Аудит и точный scope.** Проверить runtime/активные работы, реальные модели и прежние политики. Опубликовать краткую карту профилей и ограниченный implementation scope. Не превращать этот этап в финальный результат.

**Исходники и тесты.** В отдельной OPS-ветке реализовать PM stage, schema/validator, routing registry, явные model/effort в запуске, учёт использования, безопасный status и replay/restart handling. Новые интеграции проверять в disposable среде, не в PROD.

**Независимая проверка.** Отдельный reviewer проверяет точный SHA механизма, а не только автора. Автор не принимает собственный planner/validator. Выполнить все обязательные CI-проверки и защитные негативные тесты.

**Контролируемая установка.** После QA и CI — backup, provenance/hash parity, установка через существующий разрешённый OPS-канал, безопасная граница переключения, сохранённый старый путь и проверяемый rollback. Не двигать product `dev` так, чтобы испортить base активной задачи; согласовать порядок интеграции runtime и продукта по фактическому состоянию.

**Практическая приёмка.** Сначала frozen/disposable примеры, затем одна уже разрешённая безопасная продуктовая DEV-задача через весь новый путь. Она не должна требовать ручного выбора модели, правки JSON или нового Owner GO на каждый внутренний этап.

Разрешённые обычные действия после получения этого утверждённого поручения выполнять самостоятельно. Если есть реальное ограничение инструментов/прав, назвать конкретную операцию и предложить минимальный разрешённый способ, а не требовать новый общий GO. Не обходить отказ инструмента другой identity, endpoint, root или cloud-agent.

## 11. Критерии приёмки

V1 принят только при доказательствах следующих результатов:

1. На VPS реально вызывается отдельная сильная модель технического PM; задача анализируется по релевантным источникам, а не только по заголовку. Точные model/effort зафиксированы и не являются неподтверждённым default.
2. Механическая, многомодульная и чувствительная задачи проходят проверку планирования на frozen входах: зависимости и риск определены обоснованно, назначения соответствуют policy, нет автоматического extra-high для всей очереди. Не обязательно делать все три задания живыми product-изменениями.
3. Как минимум два реально доступных допущенных execution-профиля подтверждены запуском и телеметрией, а не только разными названиями в плане. Указать честно, различаются они моделями или только effort; не называть второе доказанной маршрутизацией между разными моделями. Неподключённые провайдеры остаются явно не принятыми.
4. Обычный код отвергает выход за parent scope, неизвестную модель, запрещённый effort/tool/path, отсутствующую зависимость, устаревший план и превышение лимита. Попытка выдать shell-команду или расширить полномочия через план не исполняется.
5. QA, ошибки провайдера, исчерпание квоты и fallback проверены без сброса общего счётчика и без двух одновременных writers. Недоступные инструменты не маскируются переключением на более дорогую модель.
6. Повторная доставка задания, restart во время planning/authoring, смена base и неизвестный исход не порождают неконтролируемые повторные вызовы и не теряют историю. Проверены compatibility/rollback checkpoints.
7. По каждому вызову есть доступные usage-данные либо явный пробел. Есть принудительные проверенные лимиты и различение подписочной квоты, дополнительных расходов и неизвестной стоимости. Экономия в процентах не заявляется без сопоставимого baseline.
8. Одна существующая Owner-approved задача проходит реальный путь: Grok → PM → валидированный план → назначенный автор → новая независимая QA → полный CI → DEV ACCEPTED и live SHA match. Её пользовательская UAT проверяется и показывается отдельно от CI/receipt; отсутствие доступа или устройства не объявляется PASS.
9. Grok показывает владельцу текущую роль, исполнителя, причину назначения, этап, расход/неизвестные показатели, blocker и следующее действие. Владелец не служит диспетчером моделей или курьером между агентами.
10. Нет нового оркестратора/очереди, скрытого cloud API, расширенных root-прав, изменений PROD/PLAN/VPN и потери прежних работ. Статус реализации содержит оставшиеся ограничения, а не формулу «всё автономно».

## 12. Формат отчёта владельцу и окончательные deliverables

Короткий рабочий статус должен выглядеть примерно так; это шаблон, не выдуманные факты:

«Задача #N. Технический PM: [фактическая модель/режим]. План: [версия]. Автор: [CLI/model/effort], выбран потому что [одна причина]. QA: [профиль]. Сейчас: [этап]. Использование: [реальные метрики / неизвестно], лимит: [значение и степень технического enforcement]. От вас: ничего / одно конкретное решение».

По окончании передать: exact PR/commit; версионированную policy и реестр профилей; схему плана; независимый QA verdict и тесты; installation/rollback evidence; результат реальной DEV-задачи; usage breakdown с неизвестными; короткий runbook для дальнейшей работы без старого чата.

Не создавать большой dashboard для первой версии. Достаточно существующего GitHub-record, машинного статуса и понятного ответа в одном OPS-чате. Документация, разработка, установленный runtime и продуктовая приёмка — отдельные факты.
