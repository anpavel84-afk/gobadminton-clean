# GoBadminton — Project Manifest v1

Дата: 2026-10-01. Основание: [Owner decisions](OWNER_DECISIONS.md). Техническая часть — **TECH_SELECTED**, продуктовые defaults — **PROPOSED_PRODUCT**, если нет отдельного Owner decision.

## Назначение

GoBadminton помогает человеку найти конкретную игру подходящего уровня, времени и места, запросить участие и получить понятное решение организатора. Организатор получает участников и меньше ручной работы. Основной объект — игра/занятие, а не каталог профилей или сайт одного клуба.

Это самостоятельный продукт. BadmintonOpen не является зависимостью, источником кода, данных или визуальной системой.

## Принципы

**Одна бизнес-система, несколько клиентов.** Web, iOS и Android работают с одинаковыми серверными правилами. Ни сайт, ни мобильное приложение не ведут собственный учёт мест.

**MVP — подмножество продукта.** Сейчас реализуются только необходимые сценарии. Расширяемость обеспечивают устойчивые идентификаторы, отдельные состояния, API и границы данных, а не пустые микросервисы.

**Сначала корректность, затем скорость.** Подтверждённое место не возникает из optimistic UI, кеша или push. Сервер атомарно проверяет лимит и права. Повтор запроса не создаёт повторную запись.

**Приватность по умолчанию.** Каталог показывает информацию об игре и согласованные публичные сведения организатора; не раскрывает provider IDs, контакты игроков и списки чужих заявок.

**Измеряем реальную ценность.** Заявка, подтверждение, состоявшаяся игра и посещение — разные факты. Истечение времени не доказывает посещение. Новый клиент не определяется исключительно рекламной меткой.

**Независимость от поставщиков.** Авторизация, карты, сообщения, object storage и платежи подключаются адаптерами. API GoBadminton не использует VK/Yandex IDs как пользовательские идентификаторы.

## Целевая система

Один TypeScript-monorepo. Backend — NestJS с Fastify, модульный монолит и отдельный worker того же source/release. Данные — PostgreSQL + PostGIS. Web — Next.js. iOS/Android — React Native + Expo в одном mobile-приложении. Публичный API — REST/JSON с версионированным OpenAPI-контрактом. Admin — отдельная защищённая поверхность того же backend.

Архитектура и альтернативы: [overview](../architecture/OVERVIEW.md), [stack](../architecture/STACK.md), [ADR](../decisions/README.md).

## Первый продуктовый контур

Рабочая модель: публичные игры → фильтры → карточка → вход VK/Яндекс → заявка → подтверждение/отказ → участие/отмена → фиксация результата. Организатор создаёт игру и делится ссылкой. Стоимость и правила расчёта показываются, но деньги через GoBadminton не проходят.

Каталог доступен без аккаунта как проектный default. Публикация и заявки требуют аккаунта. Первый пилот фокусируется на небольшом числе организаторов; разрешение на массовую самостоятельную публикацию не следует из наличия роли в модели.

## Долгосрочные границы

Архитектура предусматривает несколько городов, локалей, устройств и провайдеров входа; команды организаторов; регулярные игры; карту; уведомления; будущие платежи и расчёты. Поддержка других видов спорта, клубной ERP и внутреннего чата не объявлена целью. Точки расширения описываются без преждевременной реализации.

## Полномочия и готовность

Владелец решает продуктовые, юридические, денежные и существенные риск-вопросы. Architect выбирает технические решения в делегированной области. PM координирует; Implementation реализует; QA независимо проверяет. Дизайн создаёт Visual Designer, не только директор/спецификатор.

Foundation завершает архитектурную постановку, но не подтверждает работающий backend, авторизацию, масштабирование, безопасность или приёмку приложений магазинами. Для этого нужны реальные срезы, тесты и отдельные release gates.
