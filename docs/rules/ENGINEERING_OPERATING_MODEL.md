## 1. Приоритет и источники истины

В пределах проекта действуют: явное решение Owner в его точной области → этот принятый регламент → предметные ADR/контракты/Style Guide → ограниченное назначение. Назначение не может само расширить standing authority, снять защиту или разрешить PROD. Новое явное исключение Owner записывается с областью и основанием; нельзя молча переинтерпретировать старое согласие. Ограничения платформы и реальные доступы не обходятся проектным документом.

| Что устанавливаем | Единственный источник соответствующего факта |
| --- | --- |
| Продуктовая цель, приоритет, связи, решения | GitHub Issues и существующий GitHub Project |
| Разрешение исполнить конкретную работу | Точный допустимый immutable admission/assignment |

Project — не диспетчер процессов; Owner Monitor — только read-only представление этих данных. Локальный JSON, чат, старая очередь или Hub не заменяют текущий backlog/authority. История не переписывается и не превращается в актуальный runtime по названию документа.

## 2. Конфигурация и границы

Рабочий репозиторий один: `anpavel84-afk/gobadminton-clean`. Другие репозитории допускаются только как явно обозначенные исторические источники; нельзя брать оттуда текущую очередь, executable launcher или полномочия. Контекст для продолжения должен быть достаточен внутри CLEAN.

Модельные задания исполняются на Germany VPS `vmi3510488` от непривилегированных служебных identities в назначенных worktrees. `PLAN` — только управление/просмотр, без авторов, QA и автозапусков. Доверенный bridge/интегратор выполняет разрешённые Git-операции; source-only автор не получает их автоматически.

Не считать фиксированный каталог текущим checkout: перед работой проверить repo identity, фактический worktree, base SHA, грязное состояние, роль и владельца lease. Существование каталога или успешный SSH не доказывают актуальность/полномочия. Deployment-каталоги не являются рабочей копией автора.

DEV — изолированные web/API/DB/media в Германии, пользовательская проверка на `dev.gobadminton.ru`. PROD — отдельные московский web и немецкие API/DB; разделение данных, credentials и сервисов обязательно. Этот документ не меняет существующий межсерверный транспорт. Не трогать сторонние проекты и VPN.

GitHub-hosted Actions управляет ограниченными этапами, а разрешённый серверный adapter исполняет их. Не возвращать старый постоянный Supervisor/Autopilot и не переносить его бесконечный цикл в workflow. Существующие два слота сохраняются; пересекающиеся пути/ресурсы сериализуются. Интеграция и DEV используют существующие отдельные блокировки.

Default branch `main`, продуктовая интеграция `dev` и установленный pin контроллера — разные вещи. Наличие нового документа/кода на одной ветке не означает обновления остальных. Нельзя ради обновления правил продвинуть весь продукт в PROD или сменить pin контроллера.

## 3. Роли и ответственность

| Роль | Делает | Не делает без отдельного назначения |
| --- | --- | --- |
| Owner — Павел | Цели, приоритеты, продуктовые решения, исключения, расходы вне разрешённого объёма, конкретный PROD GO | Не является курьером файлов и источником повторных micro-GO |
| Advisor | Ревизия, продуктовые/технические рекомендации, подготовка документов в разрешённой ветке | Не становится вторым PMA или параллельным оператором |
| PMA | Один оперативный координатор: backlog, постановки, проверка scope/маршрутов, допуски, зависимости, контроль результата и эскалация | Не выдаёт собственное утверждение за QA и не меняет инфраструктурные ограничения ради старта |
| Технический PM / planner | По коду и задаче оценивает этапы, сложность автора и QA, риски; предлагает exact маршруты и fallback | Не утверждает за Owner новую архитектуру/полномочия и не подменяет исполнителя |
| Автор | Только назначенный ограниченный срез, код/тесты, самопроверки, handoff | Не выбирает следующую задачу, не правит свою admission/бюджеты, не принимает свою QA |
| Независимый QA | Отдельный контекст и защищённая роль, проверка exact candidate и критериев | Не ремонтирует этот candidate внутри той же QA-сессии и не фабрикует результаты |
| OPS/интегратор | Отдельно разрешённые host/adapter/workflow изменения с review, backup и rollback | Не использует продуктовый scope как общее root/PROD разрешение |

PMA ставит цель техническому PM и проверяет предложенную таблицу, а не сочиняет доступные model IDs по памяти. Внутри принятой матрицы, существующей делегации и допуска повторный Owner GO не требуется. Новый класс полномочий, затрат, риска или маршрут за пределами допуска требует отдельного решения. Специалисты Product/Design/Architect подключаются по реальной необходимости, не к каждой CSS-правке.

## 4. Задача и автономный цикл

Один пользовательский результат — одна родительская карточка; связанные этапы/подзадачи допустимы, если сохраняют цель, историю и дают осмысленные проверяемые приращения. Не дробить работу так, чтобы следующий этап переписывал предыдущий. Постановка содержит результат для пользователя, границы, зависимости, точные входы, acceptance и способ проверки.

Перед исполнением PMA обязан различить:

- BACKLOG: постоянная запись требования, не разрешение запуска;
- READY/ADMITTED: выполнены зависимости и существует корректный immutable допуск;
- IN_PROGRESS: подтверждён реально запущенный этап, а не только название модели;
- BLOCKED/DEFERRED: точная причина, evidence, ответственный и следующий допустимый шаг;
- SOURCE_READY, QA_PASS, CI_PASS, DEV_ACCEPTED, OWNER_ACCEPTED и PROD_RELEASED: отдельные подтверждённые факты.

Для обсуждаемой задачи — обычный Issue и единственный неизменяемый Owner admission-комментарий по действующему протоколу. Не оставлять одновременно валидные body- и comment-admissions. Не править admission задним числом и не выдавать комментарий Advisor, label, Project status или новый Markdown за машинный допуск. Ранее принятые V1 назначения сохраняют свою семантику.

Цикл: `claim → author → publish → independent QA → CI → integrate → promote to dev → DEV verification`. Если интеграция изменила candidate SHA, применяются действующие проверки нового candidate; старый PASS не переносится автоматически. Контроллер продолжает следующие допущенные независимые задачи без micro-GO; отдельный автор заканчивает свой срез и возвращает управление контроллеру.

Закрытый чат не считается остановкой или работой train: подтверждение берётся из реального контроллера. При обычной ошибке продолжаются независимые задачи; зависимые ждут завершённого результата. Не выдавать создание Issue/PR за запуск или поставку.

### 4.1. PMA доступен через ChatGPT Work или Grok-бота

**PMA — одна логическая управленческая роль, а не конкретная модель, чат или бот.** Owner может работать с ней из ChatGPT Work или Grok-бота. Оба интерфейса должны ссылаться на те же GitHub Issues/Projects, immutable authorizations, Actions train и root receipts. Переключение интерфейса не переносит очередь, не обнуляет attempts, не останавливает процессы и не создаёт второго параллельного управляющего или второго source writer.

Перед любым изменяющим действием любой интерфейс повторно читает текущие task/lease/checkpoint/installed rules SHA и проверяет полномочия действующей идентичности Owner. Одновременные команды из двух интерфейсов проходят через существующие атомарные authority/idempotency/lease gates; конфликтующие изменения отклоняются или сериализуются. Текст сообщения или факт подключения Grok-бота не являются сами по себе машинным допуском либо подтверждением полномочий. Нельзя переносить токены, сессии или секреты между чатами ради непрерывности.

Готовность интерфейса проверяется отдельно: реальное чтение состояния и безопасное авторизованное действие с проверкой отказа чужой/повторной команды. **Наличие Grok-бота у Owner — требование к доступности PMA из двух каналов; подключённый к действующему протоколу полноценный Grok-бот без evidence не объявляется VERIFIED.** Новая очередь, второй PMA и постоянный GPT-чат для мониторинга не нужны.

## 5. Кто и как выбирает модели

Порядок выбора: **характер этапа → риск/сложность → необходимая способность → разрешённые доступные маршруты → стоимость и остаток ресурса**. Не выбирать дорогую модель потому, что она доступна, и не направлять критическую задачу слабой модели только ради равномерного расхода квот.

Технический PM отдельно оценивает сложность разработки и сложность проверки. Сложный автор не делает автоматически сложной каждую QA; простая форма, контакты, обычный CRUD или известная UI-правка не являются основанием для Astra High **как обычной QA**. Отдельное прямое Owner-решение назначает Astra High экспертом по подтверждённым содержательным QA/CI FAIL перед очередной доработкой, даже если исходная QA была простой. Сначала детерминированные проверки и чтение конкретного failure, затем нужная модельная работа.

| Этап | Предпочтение в целевой конфигурации | Допустимый резерв при подтверждённой способности |
| --- | --- | --- |
| Механическая правка по ясной спецификации | Cursor Auto; при подходящем scope Codex Luna Medium | Codex Sol Medium |
| Обычная разработка, формы, CRUD, UI | Cursor Auto | Codex Sol Medium |
| Сложная реализация/диагностика | Подходящий квалифицированный Cursor маршрут либо Codex Sol High | Обоснованная эскалация, не автоматическое Astra High |
| Критическая архитектура, threat model, безопасность/конкурентный доступ, трудный инженерный блокер | Codex Astra High с конкретным основанием | Отдельное экспертное решение в допустимой области |
| Обычная независимая QA | Квалифицированный Antigravity маршрут подходящего уровня | Codex Sol Medium в отдельной защищённой QA-роли |
| Сложная QA | Квалифицированный Antigravity или Codex Sol High по предмету | Astra только при доказанной экспертной необходимости |\n| Диагностика подтверждённого содержательного QA/CI FAIL перед доработкой | **Codex Astra High, отдельная экспертная стадия по Owner decision** | Если недоступна — явное ожидание или специально утверждённый эквивалент; не подменять молча обычной QA |
| Исследование, источники, каталог контента | Квалифицированная исследовательская роль Antigravity | Другой разрешённый исследовательский маршрут |
| Тесты, сборка, CI, release machinery | Детерминированные инструменты/Actions | Не заменять лишними модельными вызовами |

Это матрица назначения, не реестр готовности и не список executable IDs. Codex участвует и как эксперт, и как резерв, и как достаточно дешёвый автор/QA; его не надо искусственно исключать.

Каждый модельный этап получает provider/client, **проверенный точный model ID этого клиента**, поддерживаемый effort, роль, причину выбора, упорядоченный fallback и границы бюджета. Брать IDs из проверенного установленного адаптера/реестра, а не из маркетингового имени, памяти модели, версии CLI или другого провайдера.

Cursor Auto — специальное разрешённое предпочтение Owner, а не право писать неопределённое «auto» везде. Различать router profile `auto`, Cursor selection `auto` и фактически обслужившую модель. Если провайдер её/effort не раскрывает, recorded effective value остаётся UNKNOWN/not exposed; не выдумывать идентичность. Для остальных явных маршрутов сохраняется exact-ID требование. Не придумывать effort для клиента, который его не поддерживает.

PMA проверяет соответствие предложенной таблицы этой политике и делегации. Действующий router выбирает только внутри допущенного упорядоченного набора с учётом роли, готовности и доступности. Сам автор не меняет свою модель, набор fallback или цену. Если нужного варианта нет — точный BLOCKED и bounded remedy, а не произвольная подмена.

Новые метаданные внедрять только через поддерживаемую схему допуска. Отдельная оценка сложности QA сначала фиксируется в постановке; не вставлять неподдерживаемые поля в immutable JSON и не обещать, что Markdown уже реализовал новый алгоритм.

## 6. Ресурсы, fallback и попытки

Различать внешнюю квоту провайдера, внутренний операторский лимит вызовов, финансовый бюджет и число попыток задачи. Нельзя выдавать одно за другое. Owner разрешил убрать искусственный дневной Codex author/QA cap в #211; это не разрешение стереть счётчики или сделать безграничными retry/затраты.

Учёт вызовов и история сохраняются и в режиме unlimited дневного cap. Реальные 429/auth/quota отказы, срок работы этапа, число попыток, concurrency и loop protection продолжают действовать. Цены/токены/остатки, которых нет в receipts, — UNKNOWN/null, не вымышленные деньги.

Предпочитать уже оплаченные подходящие маршруты и избегать простаивающей пригодной квоты при истощении другого клиента, но только после проверки способности, роли и безопасности. Unknown quota не означает бесплатность или доступность.

Fallback до запуска допустим внутри точного допуска. После timeout/потери связи сначала установить, завершился ли прошлый процесс и остались ли эффекты/lease; неизвестный writer не дублируется. Отказ до фактического author запуска не выдаётся за дефект кода. Существующие ledgers не переписываются: расхождение классификации исправляется через reviewed учётный механизм, не ручной reset.

После исчерпания попыток — конкретная диагностика и штатный bounded RESUME/преемник по действующим правилам с сохранением всей истории. Не создавать бесконечную цепочку новых Issues ради обнуления 3/3. Новые решения/бюджеты вне standing authority — Owner. Исправления среды и повторное выполнение того же дефекта должны различаться в отчёте.

## 7. Безопасность как условие работающей системы

Цель — Cursor, Codex и Antigravity работают в необходимых ролях с сохранёнными границами, а не отключены навсегда «ради безопасности». Недоступность предпочтительного исполнителя — отдельная обязанность устранения, а не выполненная целевая конфигурация.

Обязательны изоляция рабочей области/других worktrees, least privilege, разделение автор/QA, защита credentials, ограниченные файловые/сетевые/процессные эффекты, timeout и прослеживаемый результат. Запрещены общий root/Docker socket, произвольный sudo, доступ автора к PROD secret/DB, глобальное снятие AppArmor и отключение защиты только ради зелёного запуска.

Конкретный механизм изоляции не равен всей политике безопасности. Узкий проверенный профиль/совместимый runtime допустим в существующем OPS scope. Замена механизма на эквивалентный требует отдельной технической проверки и штатного допуска; автор не принимает это решение сам. Не обходить отказ инструмента/платформы другой обёрткой или машиной.

Каждый отказ содержит версию, роль, безопасный текст ошибки/код, точную запрещённую операцию и remediation Issue. AppArmor/userns конфликт сам по себе не доказывает невозможность безопасного Cursor. Успешный probe запуска не доказывает допустимость продуктового author или QA.

Для Antigravity отдельно проверяются весь CLI/tool contract, реальные ограничения чтения/записи/сети/credentials, распространение отказов, корректность парсинга, достаточность контекста, обработка имён файлов и requested/effective model receipts. Совет или текст «PASS» без этих свойств не становится независимой QA.

Существующие точечные Owner exceptions сохраняют только исходный reviewed scope/installer/hash/срок. Они не являются общей отменой защиты. Не переносить исключение одного установщика на другой; авторские комментарии внутри скрипта не создают waiver. Установка — через существующий доверенный OPS путь с backup/rollback и безопасной границей активной работы.

## 8. Независимая QA и приёмка

Минимум независимости: новый контекст проверки, separate protected QA role, недоступность записи в candidate/author state и достоверный verdict на точный SHA. Другой провайдер предпочтителен, когда квалифицирован; сам по себе другой бренд модели не даёт независимости. Раздельные сессии того же провайдера допустимы только по действующему подтверждённому QA механизму.

QA проверяет diff, предметные критерии и затронутые риски; не проводит бесконечный повторный аудит неизменённой системы. При изменении threat boundary нужен соответствующий review. Авторская самопроверка, статический check, независимое суждение QA, CI и live smoke — отдельные результаты.

Недоступность зависимостей в офлайн author/QA среде означает NOT_TESTED для локального запуска; код и тесты всё равно должны быть подготовлены. Если проверка обязательна, её выполняет разрешённый CI/verification этап до приёмки. Нельзя подменять это ложным PASS или бесконечно требовать сети у заведомо офлайн автора.

DEV завершён только при точном прошедшем candidate, обязательных CI jobs, paired immutable artifacts, подтверждённом ACCEPTED и соответствующем live результате. Числа «написано/слито/проверено/выложено/принято Owner» не смешивать. Для контентной задачи нужен заполненный и проверенный каталог, а не только инструмент импорта.

PROD — отдельное явное решение Owner на точный выпуск и действующие release gates. Проверенный DEV не разрешает PROD автоматически. App rollback не равен DB rollback; не восстанавливать БД поверх новых writes без отдельного плана сохранности данных.

### 8.1. Непрерывный цикл доработки: FAIL → диагноз → исправление → новая проверка

**Нормальная задача не заканчивается после первого QA/CI FAIL.** Конкретный отчёт о проблеме с exact SHA, тестом/логом, ожидаемым и фактическим результатом поступает обратно в действующий авторский маршрут. Порядок:

1. **Автор** создаёт ограниченный source candidate и собственные тесты; публикация через доверенный Git/PR bridge.
2. **Детерминированные проверки** выполняются в предусмотренном действующим route порядке. Если они падают, конкретный CI/test failure должен быть зафиксирован до очередного модельного вызова.
3. **Независимая QA** проверяет ровно текущий candidate SHA и критерии задачи. При FAIL сохраняет findings, не исправляет код в собственной сессии.
4. **Экспертная оценка FAIL — Codex Astra High**: подтверждённый содержательный QA FAIL или CI FAIL по исходникам автоматически направляется на отдельную ограниченную стадию `failure_diagnosis` к квалифицированной Astra High **до следующей авторской доработки**. Дать ей exact candidate SHA/diff, исходное assignment, конкретные findings, упавшие тесты/логи, историю уже предпринятых исправлений и доступные контракты. Astra проверяет причину, устраняет противоречивые прежние гипотезы и возвращает проверяемый repair brief: корневая причина с evidence/уверенностью; минимальные допустимые изменения; какие тесты/инварианты надо исправить или добавить; угрозы регрессии; разрешённый авторский маршрут/уровень сложности. Она не пишет код в роли QA, не расширяет allowed_paths/бюджеты и не объявляет PASS.
5. **Исправление по brief Astra**: если число author attempts ещё в пределах неизменяемого разрешённого бюджета (обычно максимум 3 всего), train возвращает того же candidate разрешённому автору вместе с диагностикой Astra. Автор меняет только разрешённый scope. Новый candidate SHA → снова детерминированные тесты → независимая QA → CI. Исходные FAIL, диагноз и прежние attempts остаются в истории.
6. **Повторный содержательный FAIL**: новый SHA/изменённые findings снова поступают на экспертную оценку Astra с историей прежнего диагноза; она должна уточнить, почему предыдущая рекомендация не устранила проблему, а не дублировать её. Не оплачивать новый вызов для той же неизменённой ошибки на том же SHA, если уже имеется пригодный hash-bound диагноз; использовать сохранённый brief. Простой preflight/environment/auth/quota failure, неверное окружение, отсутствующий инструмент или недоступность модели прежде всего обрабатываются соответствующим OPS/reconcile путём и не называются дефектом исходников.
7. **QA/CI PASS** ведут через контролируемую интеграцию. Если интеграция меняет SHA или DEV ушёл вперёд, применяются обязательные fresh gates. DEV deployment/smoke PASS и ACCEPTED — отдельный факт. При DEV fail — установленный rollback/reconcile и предметная диагностика, не слепая автоматическая публикация того же результата.
8. **При исчерпании 3/3** первоначальная задача становится DEFERRED/не DONE. Действующий bounded recovery #185 может использовать экспертный диагноз Astra для diagnose → independent task review → одной отдельно связанной ограниченной задачи-преемника только при действительной делегации, admission, allowed paths и lineage budget. Исходные 3/3 не сбрасываются; у преемника собственный явно допущенный конечный лимит (в действующей схеме обычно 2). После неуспеха преемника либо недостатка authority — NEEDS_OWNER/точный blocker, а не бесконечные новые Issues.
9. **Неизвестный результат** модельного вызова, процесс, который может ещё писать, отказ auth/provider, отсутствие инструмента или транспортный timeout **не являются QA FAIL или разрешением потратить следующую авторскую попытку**. Сначала сверяются PID/lease/operation/checkpoint/receipts; никакого второго writer или повторного списания вслепую.


Такая доработка не требует повторного Owner GO внутри уже выданного scope и работающей recovery-делегации. Owner привлекается только при действительно новом продуктово-опасном выборе, расширении scope/бюджета или отсутствии разрешённого безопасного продолжения. Локально проблемная задача не тормозит независимые допущенные задачи в другом слоте.

**Статус реализации:** обычный author repair и ограниченный механизм #185 предусмотрены существующим Actions train. **Обязательная экспертная Astra High стадия между новым содержательным QA/CI FAIL и авторской доработкой — новое Owner-решение, требующее отдельной ограниченной реализации/подтверждения в текущем маршрутизаторе; наличие этого текста ещё не означает, что controller выполняет её.** До установленного подтверждения PMA организует допустимое экспертное заключение через существующую разрешённую OPS-процедуру либо указывает конкретный blocker; не подделывает автоматизацию и не переписывает старые immutable admissions. Полное автоматическое завершение сценария 3/3 → successor → DEV также требует точных runtime receipts.

## 9. Наблюдаемость и восстановление

По каждому provider × role показывать: установлен ли клиент; доступен ли нужной identity; проходит ли защищённый реальный запрос; известна ли квота; подключён ли маршрут к pipeline. Итоговая готовность: READY / DEGRADED / UNAVAILABLE / NOT_TESTED, время, версия, evidence и следующий шаг. Эти значения — динамические данные, не навечно записанные в правилах статусы.

READY требует role-specific end-to-end proof. CLI help, подписка, модель в списке, календарная дата восстановления квоты и read-only probe этого не заменяют. При изменении бинарника, профиля, роли или границ перепроверять затронутые свойства. Не делать платный полный повторный commissioning перед каждой обычной задачей без причины.

В задаче показывать выбранный и effective маршрут, причину fallback/escalation, текущий этап, реально работающий процесс либо отсутствие такового, последнее подтверждённое событие, attempts и стоимость/usage в доступной точности. Старые данные маркировать stale, не выдавать время обновления страницы за прогресс.

О блокировке предпочтительного провайдера, остановке train, постоянном дорогом fallback или необходимости Owner action сообщать явно. Использовать существующий серверный watchdog/уведомления; периодический GPT-чат не является заменой надёжного мониторинга. Настройка SMTP без подтверждённой доставки не называется работающим alarm.

PMA сначала читает конкретную ошибку/логи, затем делает минимальное исправление в разрешённом scope. Не перезапускает всё вслепую и не создаёт параллельного исполнителя. Непересекающиеся задачи продолжаются при локальном сбое.

## 10. Экономия контекста и доказательства

**Browser last resort для оперативного управления:** GitHub API/CLI, Actions logs/artifacts и разрешённые серверные данные — основной канал. Браузер — одна целевая проверка недоступного программно критичного факта или требуемого пользовательского/визуального сценария. Не заменять обязательный визуальный тест чтением DOM/логов. Не повторять уже принятый аудит без изменения проверяемого риска.

[Project Record Policy](PROJECT_RECORD_POLICY.md) определяет хранение: код и текст — GitHub; бинарные макеты, скриншоты и архивы evidence — разрешённое закрытое хранилище с hash и ссылкой. Не коммитить секреты/сессии/личные данные или распечатывать их для доказательства доступа. Не использовать Owner как курьера между ролями.

## 11. Загрузка правил и управление изменениями

Обязательный вход — корневой [AGENTS.md](../../AGENTS.md), затем этот документ целиком, затем exact assignment и ограниченный предметный контекст. Cursor rule и GitHub instructions — короткие указатели, не самостоятельные копии матрицы. Nested instructions уточняют технологию модуля, не расширяют полномочия.

PMA/адаптер передаёт принятую ревизию правил в контекст и фиксирует её SHA в preflight/handoff. Простое наличие ссылки не доказывает чтение. Для каждого реально используемого CLI при подключении/изменении способа загрузки проверяется, какие инструкции попали в сессию; для не поддерживающего autoload клиента текст включается разрешённым launcher. Неподтверждённый автоподхват Antigravity не заявляется работающим.

Автор не может ослабить собственный QA-policy изменениями в candidate. Новая редакция правил рассматривается по предыдущей принятой редакции и явному Owner scope. При конфликте остановить только спорный эффект, сохранить работу и обозначить конкретное противоречие; не выбирать удобный старый текст.

Операционные инструкции этого документа заменяют прежние несовместимые утверждения в entrypoints, Cursor onboarding/workflow/map, старом GoBad регламенте и начальном ChatOps-пакете. Продуктовые решения, domain/security contracts и исторические evidence не отменяются. Файлы `docs/workbench/`, `docs/handoffs/`, старые prompts, dated commissioning и `_automation/` не являются текущей очередью или разрешением запускать процессы.

Изменения через docs PR: точный scope, причина, supersession, проверка ссылок/остатков, независимое review по риску и штатные проверки. Не поддерживать альтернативный «финальный» файл или новую версию только в чате. Применять обновление к новым задачам/безопасной границе; не переписывать активные immutable admissions.

PMA обязан синхронизировать документацию в ветках/launchers, откуда реально стартуют роли. Docs-only перенос на default/controller reference не должен захватывать продуктовый код, менять pin или ослаблять checks. До подтверждения различать DOCUMENT_PUBLISHED и RULES_EFFECTIVE; до role-specific commissioning — RULES_EFFECTIVE и PROVIDER_READY.
