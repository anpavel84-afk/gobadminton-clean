Схема показывает роли и порядок, не дополнительные сервисы. Если после интеграции изменился candidate, применяются обязательные проверки новой версии. Owner Monitor и существующий немодельный watchdog наблюдают этот контур; не управляют второй очередью.

**Что называем runner:** существующий ограниченный серверный исполнитель Actions-заданий, а не прежний самостоятельный Runner/Autopilot и не постоянно открытый чат. **Train:** весь цикл от допущенной задачи до проверенного DEV. **Adapter:** проверенный способ вызвать конкретный клиент/модель в разрешённой роли. **Receipt:** запись о фактическом запуске/результате; не всякая запись является криптографически подписанной.

**Исполнение на Германии** относится к автоматическим процессам, работающим с проектными файлами и инструментами. Сам диалог PMA может находиться в ChatGPT или Grok. `PLAN` — только просмотр/управление, не автор, QA или место автозапуска.

Не считать каталог актуальной рабочей копией по имени: сверять repo identity, origin, worktree, branch/base SHA, dirty state, владельца и потребителей. `main`, продуктовый `dev`, candidate SHA и установленный controller pin — разные версии. Перенос документов не является продвижением всего dev в main или изменением контроллера.

### 2.1. Два слота и один путь исполнения

Слоты — две существующие ограниченные исполнительные ёмкости, а не постоянные привязки «слот 1 = Cursor». Каждый получает только разрешённую стадию/роль. Независимые задачи могут выполняться параллельно; пересечение файлов, данных, shared fixtures или ресурсов требует действующих locks и сериализации.

Один writer на задачу и пересекающийся scope. QA и диагностика работают с неизменяемым снимком, не с одновременно изменяемой копией автора. Интеграция и DEV сериализуются существующим механизмом; неизвестный исход публикации сохраняет reservation до reconciliation.

Неполадка одной задачи не блокирует независимые допущенные задачи. Нельзя освобождать ресурс только потому, что чат закрылся или SSH оборвался. Сначала установить фактическое состояние процесса и эффектов. Новый provider не получает новый обходной канал исполнения.

## 3. Роли и ответственность

| Роль | Ответственность | Не имеет права |
| --- | --- | --- |
| Owner — Павел | Цель, приоритеты, продуктовые изменения, исключения, конкретный PROD GO | Не обязан переносить файлы и повторно давать GO на каждое исправление |
| Advisor | Независимые рекомендации, ревизия, разрешённая подготовка спецификаций | Создавать параллельного PMA или незаметно управлять активным runtime |
| PMA | Единая координация: backlog, постановки, допуски, зависимости, результат, эскалация | Подменять независимую QA своим заверением, ослаблять защиту ради запуска |
| Технический PM / planner | Читать задачу и код; планировать этапы; отдельно оценивать автора/QA; предлагать маршруты | Выдумывать model IDs, расширять продукт или author authority |
| Автор | Код/тесты и самопроверка ограниченного задания | Принимать собственную QA, менять допуск/бюджеты, выбирать следующую задачу |
| Независимая QA | Проверять exact candidate по критериям и рискам, выдавать findings | Исправлять candidate в той же сессии и затем считать это независимой проверкой |
| Эксперт FAIL — Astra High | Разбирать содержательную неудачу, искать причину, выдавать точный repair brief | Объявлять исправление принятым, снимать gates, напрямую писать код в диагностической роли |
| OPS/интегратор | Отдельно разрешённые изменения host/adapter/workflow с review и откатом | Использовать продуктовую задачу как общее root/PROD разрешение |

Роль не равна бренду модели. Одна модель может участвовать в разных ролях только отдельными сессиями с соответствующими правами; название роли не доказывает независимость. Astra, написавшая repair brief, не принимает исправление вместо независимого QA.

PMA ставит цель техническому PM и проверяет его рекомендацию в пределах делегации. Planner не становится вторым диспетчером. Product/Design/Architect подключаются по реальному предмету работы, не к каждой CSS-правке.

## 4. Постановка, управление и автономия

Один пользовательский результат — одна постоянная родительская карточка. Допустимы связанные этапы, если они имеют проверяемый смысл и не заставляют последующий этап переписывать предыдущий. Backlog-запись не является запуском. Полноту требования проверяют по исходным критериям, а не числу закрытых подзадач.

До допуска нужны: цель; accepted rules revision; exact source/design inputs; scope/allowed paths и эффекты; зависимости/locks; acceptance; проверки; отдельные author/QA маршруты и fallback; конечные бюджеты; способ отката при применимости. Оценки и предложения не равны принятому assignment.

Для обсуждаемой задачи использовать предусмотренный действующим протоколом единственный immutable admission; не оставлять одновременно валидные body- и comment-допуски. Не редактировать старый допуск задним числом. Автоматически опубликованный преемник допустим только при проверяемой standing delegation и поддерживаемом доверенном протоколе, не из произвольного bot-комментария.

### 4.1. Один PMA через ChatGPT Work или Grok-бота

Owner выбирает среду диалога, а не новую систему разработки. Оба интерфейса читают одну очередь, одни решения, ревизию правил и факты исполнения. Полноценный PMA в Grok — разрешённая целевая альтернатива ChatGPT, а не прежнее ограничение Grok исключительно ролью courier. Ранее сохранённый courier-mode может остаться транспортом, но не определяет полномочия PMA в другой роли.

Переключение: новый интерфейс проверяет доступ/идентичность и принятые правила → читает durable handoff и текущие assignments/checkpoints → показывает занятую работу и следующий допустимый шаг → продолжает управление без перезапуска. Передача секретов через чат не требуется и запрещена; каждый канал использует собственный разрешённый доступ.

Одновременно может быть несколько экранов просмотра, но только один согласованный поток изменяющих управленческих команд. Действующий доверенный механизм должен отклонять повторные/устаревшие/конфликтующие команды по состоянию, идентичности и ключу операции. Если для PMA-команд такая защита ещё не реализована, до её приёмки изменяющие действия разрешены лишь одному выбранному каналу, второй — read-only. Замок source writer сам по себе не доказывает защиту всех PMA-команд.

Новая сессия PMA не повторяет старт автора, а читает уже начатую операцию. Пропажа чата не означает отмены. Явный STOP/CANCEL — отдельная проверенная команда через действующий механизм с сохранением checkpoints. Grok-бот не объявляется подключённым только по наличию подписки или проекта.

**Граница автономии:** принятые задания и разрешённые циклы исправления продолжаются без открытого чата. Неутверждённая новая цель или решение вне делегации не возникают сами: такой пункт ожидает PMA/Owner, а независимая допущенная работа продолжается.

### 4.2. Общая последовательность

Для новых маршрутов: подготовка/допуск → claim → author → publish → детерминированные CI checks → independent QA → подтверждение всех gates → integrate → повтор необходимых проверок нового SHA → promote в dev → DEV smoke/ACCEPTED → проверка результата. QA и CI — разные обязательные факты; ранее принятые задания сохраняют свой порядок до штатного перехода.

Любой содержательный FAIL до следующего source repair проходит экспертный цикл раздела 8.1. Infra/transport/unknown идут по отдельным ветвям, не выдаются за плохой код. Технический DEV success, продуктовая приёмка Owner и PROD release не сливаются в одно DONE.

Названия стадий/полей в документе — логический контракт, не разрешение вставлять неизвестные ключи в существующий wire JSON. PMA сопоставляет их с поддерживаемой версией протокола; отсутствие поддержки оформляется как implementation gap.

## 5. Выбор клиентов и моделей

Порядок: **этап и предмет → риск/сложность → необходимая способность → разрешённые квалифицированные маршруты → стоимость и ресурс**. Квота не делает слабую модель подходящей для критической задачи. Дорогая доступная модель не становится обычной QA по умолчанию.

Planner отдельно оценивает сложность разработки и проверки. PMA проверяет матрицу; router выбирает внутри допущенного набора. Author не меняет себе маршрут. Owner override сохраняется явно и не затирается оптимизацией.

| Работа | Целевое предпочтение | Резерв / ограничение |
| --- | --- | --- |
| Механическая правка | Cursor Auto или подходящий Codex Luna Medium | Codex Sol Medium |
| Обычная разработка, формы, CRUD, UI | Cursor Auto | Codex Sol Medium |
| Сложная реализация/диагностика вне FAIL-цикла | Квалифицированный Cursor маршрут либо Codex Sol High | Эскалация по конкретной необходимости |
| Критическая архитектура, безопасность, конкурентный доступ, трудный блокер | Codex Astra High | Отдельное обоснованное экспертное решение |
| Обычная независимая QA | Подходящий квалифицированный Antigravity | Codex Sol Medium в независимой защищённой роли |
| Сложная QA | Подходящий Antigravity или Codex Sol High | Astra лишь при доказанной экспертной необходимости |
| Содержательный QA/CI FAIL перед доработкой | **Codex Astra High — отдельная failure_diagnosis** | Нет молчаливого понижения; ожидание или специально разрешённый эквивалент |
| Исследования, источники, контент | Квалифицированная роль Antigravity | Другой разрешённый исследовательский маршрут |
| Тесты, сборки, CI, доставка | Детерминированные инструменты/Actions | Не заменять их лишними модельными вызовами |

Эксперт FAIL — прямое дополнительное решение Owner: Astra участвует и после простой QA, если та выявила содержательный дефект. Это не делает саму обычную QA дорогой и не разрешает ей пропускать проверки.

Таблица содержит семейства/уровни, не executable model IDs и не обещание их текущей доступности. Точный клиент, model ID и поддерживаемый effort берутся из проверенного установленного registry. Нельзя переносить ID между клиентами, угадывать его или выдавать версию CLI за модель.

Различать router profile `auto`, разрешённый Owner выбор `Cursor Auto` и реально обслужившую модель. Если Auto не раскрывает backend model, effective model — UNKNOWN/not exposed, а не придуманное имя. Неподдерживаемый effort — not applicable, не имитация точности.

Каждый этап сохраняет requested/effective route, причину выбора/fallback/escalation и evidence доступности. Если пригодного разрешённого маршрута нет, блокируется этот этап с конкретной remediation. Простой flip enabled без role qualification запрещён.

## 6. Бюджеты, попытки и повторные вызовы

Разделять внешнюю квоту, внутренний дневной cap, деньги, число author attempts и лимит recovery всей цепочки. Снятие искусственного Codex cap по #211 не отменяет учёт, реальные provider limits, timeouts, concurrency и конечные бюджеты задачи. Unknown usage/цены остаются UNKNOWN/null.

Предпочитать уже оплаченный достаточный маршрут и разумное использование квот после проверки способности/безопасности. Не вводить скрытую платную замену или безлимитный цикл ради непрерывности.

Обычный допуск часто содержит **до трёх author attempts всего, включая первый**, а не три ремонта после него. Точное число берётся из неизменяемого assignment. Диагноз Astra учитывается отдельным модельным этапом: не обнуляет author attempts и не расходуется бесконечно. Число экспертных вызовов/повторов ограничено допуском и общим lineage budget; неподдерживаемый бюджет сначала реализуется штатно.

Повтор события не запускает второй платный вызов. Для диагноза сохраняется ключ, привязанный к задаче/допуску, candidate, проверкам/findings, релевантному evidence и rules revision. Тот же неизменённый FAIL использует сохранённый пригодный brief. Изменённый код, новые findings или опровергнутое evidence требуют нового разбора, а не слепого повторного использования.

Fallback до запуска — только из допущенного набора. После потери связи сначала reconcile процесса/receipt/эффектов. Неизвестный вызов нельзя повторить лишь потому, что не пришёл ответ. Пропуск платного вызова и отсутствие source-дефекта фиксируются честно; существующие ledgers не исправляются ручным reset.

При исчерпании лимита — ограниченный пересмотр по разделу 8.1. Новый Issue не является способом обнулить старую историю. Разрешение продолжить внутри scope не является разрешением увеличить бюджет.

## 7. Защищённая работа исполнителей

Цель — работоспособные Cursor/Codex/Antigravity с проверенными границами, не вечное отключение «для безопасности». Но доказанный дефект изоляции не снимается из-за удобства или успешного exit code.

Модель имеет рабочий доступ к исходникам и необходимым сервисам GoBadminton в пределах доверенного DEV-контура. Права **записи** остаются ограниченными назначенным worktree/allowed_paths; исходники чужой активной задачи, интеграция, Git/publish/deploy и контрольные файлы не меняются напрямую. Чтение обычных файлов соседнего GoBadminton DEV-каталога само по себе не является критичным нарушением. Защищённые границы: PROD data/credentials, root, Docker socket, произвольный sudo, административные GitHub/CI/installer полномочия, конфигурация доверенного контроллера и сторонние проекты. Git/publish/deploy выполняет доверенный bridge.

### 7.1. Доступ к ключам по реальному риску — решение Owner от 22.10.2026

**Не считать каждый API-ключ или межкаталожный доступ критическим секретом.** Owner принимает риск ограниченного чтения доверенными Cursor/Codex/Antigravity **отзываемых проектных DEV/тестовых** API-ключей и конфигураций внутри GoBadminton. Случайная читаемость такого ключа из другой GoBadminton DEV-рабочей области — **не автоматическая блокировка исполнителя и не основание часами перестраивать sandbox**, если ключ не даёт опасных полномочий. Классифицировать по действительным правам и последствиям, а не по имени файла или факту выхода из worktree.

| Класс | Примеры и границы | Решение |
| --- | --- | --- |
| Низкий риск — допустимое проектное чтение | Тестовые/синтетические значения, ограниченные отзывные DEV-ключи, неадминистративная DEV-конфигурация без доступа к PROD и другим проектам | Доступ доверенного исполнителя разрешён в разумно необходимом DEV-сценарии, в том числе между рабочими областями GoBadminton; не создавать отдельное блокирующее security-исследование |
| Управляемый риск — рабочая авторизация и оплачиваемые провайдеры | Действующая учётная сессия Cursor, ограниченные ключи внешних DEV API, сервисы с расходуемой квотой | По возможности **использовать существующую авторизацию**, соблюдая поддерживаемый механизм клиента, минимальную область полномочий, учёт расходов и возможность отзыва; не создавать новый платный API-режим только ради пустого HOME |
| Высокий риск — обязательная строгая граница | PROD DB и реальные данные пользователей, выпуск в PROD, root/SSH/широкий PAT, административные ключи сервера/репозитория/контроллера, доступ к сторонним проектам или токен с неограниченными расходами | Не предоставлять source-only автору/QA; требовать реальной разграниченной идентичности и проверенной технической защиты |

**Видимость не равна публикации:** допустимый для работы ключ не вставлять в Git, Issue, PR, prompt, пользовательский ответ, публичный лог или QA evidence. Модель не должна произвольно выгружать ключи, изменять права, публиковать секреты или обходить ограничения платформы. Неустановленные права ключа проверяются адресно, без повторного глобального аудита всех credentials.

**Cursor — основной разработчик.** Сохранять установленную рабочую авторизацию: отсутствие login-файла в намеренно пустом HOME не означает неисправность Cursor. Предпочитать повторное использование штатного рабочего входа через разрешённый контур, а не бесконечные пробы иных способов login. Отдельный API-ключ и потенциально иной способ тарификации вводить только после проверки необходимости и стоимости, а не автоматически.

**Приёмка изоляции должна быть пропорциональной.** Техническая граница применяется там, где возможен существенный ущерб: критичные credentials, PROD, другие проекты, привилегированные эффекты или запись вне разрешённого scope. Symlink/файловые инструменты, CLI и дочерние процессы проверяются на **эти реальные границы**, а не на невозможность чтения любого безвредного синтетического файла за пределами worktree. Ранее выявленный Cursor symlink escape остаётся сохранённым finding; новая политика не выдаёт прежний FAIL за PASS, а требует установить, достигал ли обход защищённого высокорискового ресурса, и адресно закрыть такую возможность. Уже действующие sandbox/AppArmor не отключать ради удобства; не возводить новое изоляционное кольцо без доказанной необходимости.

**Приоритет PMA — вернуть Cursor в рабочий author-route.** На одном точном сохранённом checkpoint определить оставшееся препятствие, сделать минимальное исправление, выполнить один осмысленный защищённый end-to-end author canary с независимой QA/CI и перейти к реальным задачам. Не повторять прошедшие AppArmor/startup/auth тесты без нового конкретного failure; Codex остаётся штатным резервом, не заменой Cursor в целевой модели. Техническая безопасность — средство обеспечения разработки, не самостоятельная бесконечная очередь.

Для Antigravity отдельно подтверждаются tool-authority isolation, CLI argv/stdin/time semantics, события denied/error, корректный parser, отказ PASS при отсутствующем контексте, допустимые filenames и requested/effective receipts. Advisory ответ не считается независимой QA.

Точные Owner исключения действуют только в исходной доказанной области/версии/сроке. Их нельзя переносить на другого installer или выдавать за blanket waiver. Platform/tool denial не обходится другой обёрткой. OPS change — exact review, backup, rollback и безопасная граница active work, без горячей подмены неизвестной операции.

## 8. QA, DEV и продуктовая приёмка

Независимость требует свежего контекста, защищённой QA-роли, неизменяемого candidate и отдельного verdict на exact SHA. Другой provider предпочтителен, когда пригоден; один бренд или другой аккаунт сами по себе независимости не доказывают. Автор или диагност не принимает своё исправление.

QA проверяет критерии, diff и изменённые риски, не повторяет полный аудит неизменившейся системы. Визуальные изменения следуют каноническому Style Guide и требуют соответствующей пользовательской проверки. Отсутствующая возможность выполнить тест локально — NOT_TESTED; обязательная проверка должна состояться в разрешённом CI/verification до приёмки. Удалять assertions, скрывать errors или объявлять PASS по тексту модели запрещено.

QA verdict, фактические CI jobs, совместимость интеграционного SHA, paired image digests, DEV ACCEPTED и live smoke — отдельные доказательства. Ни одна зелёная галочка не заменяет остальные. Ожидание CI не является занятым модельным процессом.

PROD — только конкретный Owner GO и действующие release gates. App rollback не означает rollback данных: нельзя восстанавливать БД поверх новых writes без отдельного плана сохранности. DEV неисправность сначала локализуется/откатывается разрешённым механизмом, затем направляется в нужный тип ремонта.

### 8.1. Обязательный цикл FAIL → Astra High → доработка

**Запрещён целевой маршрут «QA сказала плохо → тот же автор пробует наугад».** Содержательный FAIL сначала разбирает Astra High.

1. Сохранить exact candidate/diff, неизменяемые требования и критерии, failed check/findings, ожидаемое/фактическое поведение и историю прошлых исправлений. Проверить, что результат действительно относится к этой версии.
2. Отличить source-дефект от infrastructure/auth/quota/transport/unknown. Не переименовывать неудобный QA FAIL в infrastructure ради обхода эксперта. При спорной причине Astra делает предметную классификацию на evidence.
3. Запустить отдельную ограниченную **read-only failure_diagnosis: Codex Astra High**. Она проверяет код, тесты, спецификацию и прежние гипотезы, а не только пересказывает сообщение об ошибке. Без нужного evidence указывает конкретный недостающий вход; не выдаёт уверенный диагноз по догадке.
4. Сохранить **repair brief**: диагноз и степень подтверждения; ссылки на доказательства; минимальные изменения внутри разрешённого scope; какие тесты/инварианты должны подтвердить исправление; риски регрессии; необходимые inputs; рекомендуемый author route; критерии новой проверки. Рекомендация эксперта не даёт новых прав или бюджета.
5. При наличии допустимой авторской попытки передать этот brief и candidate квалифицированному автору. Если эксперт предлагает иной маршрут/файлы за пределами admission, нужен поддерживаемый пересмотр/новое разрешение; не редактировать исходный immutable JSON.
6. Автор исправляет и публикует новый candidate через bridge. На новой версии выполняются детерминированные проверки и новая независимая QA; после интеграции — необходимые fresh gates. Диагноз Astra не является QA PASS.
7. Новый содержательный FAIL возвращается Astra вместе с предыдущим brief и diff ремонта. Она выясняет, почему исправление не сработало: ошибочный диагноз, неполная реализация, новый дефект или проблема критериев. Нельзя бесконечно повторять одинаковые указания. Идентичный неизменённый FAIL не оплачивается повторно.
8. После исчерпания первоначального лимита задача остаётся DEFERRED, не DONE. Существующий bounded recovery #185 может использовать диагноз для независимого review пересмотренной постановки и **одного** связанного преемника при реальной делегации/протоколе. Обычно предусмотренный лимит преемника — до двух попыток, но это не универсальное право на пять запусков: проверяется конкретная действующая policy. Старые 3/3, FAIL и lineage остаются неизменными.
9. Если преемник не прошёл, scope/authority недостаточны либо исчерпан общий бюджет, фиксируется NEEDS_OWNER с предметным решением. Независимая очередь продолжается. Не плодить новые задачи ради бесконечных повторов.

| Событие | Следующее действие |
| --- | --- |
| QA/CI обнаружили дефект кода, теста или неполную реализацию | Astra diagnosis → bounded author repair → новые проверки |
| Проверка не стартовала из-за auth/quota/зависимостей/сервиса | Bounded OPS/preflight recovery; не считать это попыткой исправления исходников без evidence |
| Timeout/оборванный канал, исход модели или push неизвестен | Reconcile PID/start/boot, lease, checkpoint и remote effects; никакого дубля |
| DEV smoke выявил продуктовый дефект | Сначала безопасное восстановление DEV; затем тот же экспертный source-repair цикл в допустимом scope |
| Ошибка требования, новый продуктовый выбор или доступ вне допуска | Точная эскалация PMA/Owner, не самовольное решение автора |

Автоматический цикл не требует micro-GO внутри установленной делегации. Если эксперт временно недоступен, ожидание должно быть видно; недопустима молчаливая замена слабой моделью. Смена QA на Astra как обычного проверяющего не реализует этот цикл.

### 8.2. Когда «недоделано» обнаружено после DEV

PMA сверяет пользовательский результат со всеми исходными критериями. Если код/тесты прошли, но обязательный сценарий отсутствует, задача не считается продуктово завершённой. Замечание Owner оформляется с воспроизведением и связью с исходным требованием, а не теряется в чате.

Невыполненный исходный критерий или регрессия → версия/связанная исправляющая задача с сохранением прежних результатов и тем же экспертным циклом. Новое пожелание сверх scope → отдельный backlog/решение Owner, не скрытое расширение старой задачи. Уже записанные QA/CI/DEV receipts не переписываются задним числом.

Например, библиотека обложек завершена после фактического наполнения и проверки каталога, не после создания импортёра. По завершении допущенной работы контроллер берёт следующую готовую задачу, не ждёт нового сообщения ради обычного продолжения.

## 9. Состояния, наблюдаемость и аварийное продолжение

Показывать раздельно: BACKLOG; готовность/допуск; действительный запуск; ожидание CI; экспертный разбор; готовый repair brief; доработка; QA/CI результаты; DEV_ACCEPTED; продуктовая приёмка; NEEDS_OWNER. Это понятные отображаемые состояния, не обещание новых wire enum без реализации.

Минимальная запись этапа: task/admission fingerprint, родитель/lineage, роль, source/candidate и rules commit/hash, controller/adapter revision, слот и operation identity, фактическое начало/завершение, exit/verdict, requested/effective model/effort, использованный бюджет и evidence. Для Astra дополнительно — failure fingerprint, diagnosis/brief revision и связь с ремонтом. Secrets и raw tokens доступа не входят в отчёт.

Provider × role имеет отдельно: установлен ли; доступен ли нужной identity; выполняет ли защищённый запрос; известны ли quota/лимиты; подключён ли к pipeline. Итог: READY / DEGRADED / UNAVAILABLE / NOT_TESTED, дата, версия и evidence. CLI help, подписка, календарь и read-only probe не доказывают author/QA readiness.

Actions events — сигналы, durable задания/checkpoints — источник восстановления. Повторные, пропущенные или запоздавшие события не должны давать повторный writer/платный вызов. Использовать существующие idempotency/leases/reconcile; новую универсальную очередь не создавать. Cancel, reboot и timeout сохраняют историю и ownership до доказанного безопасного продолжения.

Немодельный watchdog сигнализирует об остановке/невозможном простое, недоступном обязательном provider и необходимости решения. Проверка реальной доставки обязательна: наличие SMTP настройки не равно работающему alarm. Owner Monitor маркирует устаревшие наблюдения; обновление страницы не равно прогрессу модели.

При проблеме PMA читает конкретную ошибку, делает минимальное разрешённое действие и фиксирует исход. Не перезапускает весь train вслепую, не скрывает постоянный дорогой fallback и не создаёт параллельного оператора.

## 10. Контекст, документы и экономия

[Project Record Policy](PROJECT_RECORD_POLICY.md) определяет долговременную память. В GitHub — код, тексты, решения, exact prompts/handoffs и ссылки на evidence. Бинарные макеты/фото/скриншоты/архивы — разрешённое проектное хранилище с hash и контролем доступа. Не коммитить secrets, сессии и личные данные. Исторические ссылки сохраняются как provenance, не authority.

В handoff достаточно exact результата, проверок/ограничений, текущей точки и следующего допустимого действия. Новый PMA продолжает по durable данным, а не просит Owner пересказать чаты. У модели должен быть необходимый предметный контекст, не всё хранилище проекта.

Для оперативного контроля сначала GitHub API/CLI, logs/artifacts и разрешённые серверные данные. Браузер — целевая проверка недоступного программно факта или обязательного визуального сценария. Это не разрешение пропустить реальную UI-проверку. Повторный полный аудит без изменения риска не нужен.

## 11. Как все обращаются к эталону и как его менять

**Root AGENTS.md → этот документ целиком из принятой ревизии → exact assignment → предметные документы.** `.cursor/rules`, GitHub instructions, bootstrap, PMA checklist и nested web AGENTS — короткие указатели/прикладные шаги, не новые самостоятельные матрицы моделей.

Trusted launcher передаёт принятую версию и фиксирует commit/content hash и состав реально поданного контекста. Проверяется отсутствие обрезки/подмены; наличие ссылки не доказывает загрузки. Клиент без подходящего autoload получает разрешённую явную передачу текста. Запись hash доказывает происхождение переданного текста, а не гарантирует безошибочное поведение модели; поэтому проверки остаются обязательными.

Политика QA/диагностики загружается из доверенной принятой ревизии вне candidate-controlled authority. Candidate instructions и пользовательские/global overrides не расширяют права. Не снимать вслепую `--ignore-rules`: оно может защищать от непроверенных инструкций; цель — доверенный context, а не включение любого файла правил.

Изменение эталона — один reviewed docs PR с причиной, областью supersession, проверкой ссылок и согласованием с standing Owner decisions. Кандидат правил проверяется по предыдущим принятым правилам. Не править активные admissions; новая редакция применяется к новым заданиям/безопасной границе через поддерживаемый механизм.

PMA синхронизирует текст на ветках и в реальных источниках запуска. Default/main и dev должны вести к одному принятому тексту; перенос только docs не тянет продуктовую ветку, не меняет controller pin и не выпускает PROD. Публикация эталона, применение контекста и реализация новых стадий отчётно разделены.

### 11.1. Завершение legacy cleanup

По #216 сначала сохранить текущие assignments, dirty work, unique commits, receipts/ledgers и средства отката; получить безопасную границу. Затем проверить реальные consumers checkout, remote, rules, user/workspace config, PATH/wrappers и GoBadminton unit/timer/cron.

Доказанно устаревшее вывести из запуска/autoload обратимо; неизвестное не удалять. Защищённый архив допустим, активный старый writer — нет. Не делать массовые удаления, killall, git reset/clean, Docker prune или отзыв credentials. Разные root/nonroot каналы доступа не считать дублями по имени host.

Один ограниченный контрольный проход должен подтвердить чистый исполнительный путь и неизменность данных. Не делать готовность ещё не подключённых Cursor/AGY условием окончания уборки: это круговая зависимость. После неё отдельно квалифицировать providers и цикл #218. Простая проверка дрейфа входит в существующий preflight, не в новый daemon.

**Приёмка эталонной системы — реальные сценарии:**

| Проверка | Что необходимо доказать |
| --- | --- |
| Контекст | Правильный repo, accepted rules commit/hash и фактически поданный текст без legacy override |
| Переключение PMA | Смена ChatGPT/Grok сохраняет задачу, attempts и процесс; повторная/конфликтная команда не создаёт второй запуск |
| Обычная задача | Разрешённый автор → реальные тесты → независимая QA → точный DEV ACCEPTED |
| QA FAIL и CI FAIL | Каждый содержательный дефект проходит Astra brief до авторского ремонта, затем новая проверка |
| Повторный FAIL | Astra учитывает историю и уточняет диагноз; идентичный результат не вызывает повторную оплату |
| Исчерпание лимита | Честный DEFERRED, ограниченный пересмотр при реальной делегации, никакой бесконечной цепи преемников |
| Два слота | Независимая работа параллельна; пересекающаяся сериализована; локальная ошибка не останавливает независимую очередь |
| Сбой процесса/связи | Reconcile вместо слепого повтора; история и учёт сохранены |
| Providers | Каждая включённая роль прошла проверку реальных инструментов/изоляции, не только CLI startup |
| Пользовательский результат | Исходные acceptance criteria выполнены; недоделка не скрыта зелёным CI |
| Сохранность и PROD | Rollback доступен, данные/другие проекты не повреждены, PROD не выпущен без конкретного GO |

Не требуется повторять весь commissioning для каждой правки: применять проверки по изменённым рискам и реальной версии. Но полный целевой результат нельзя объявить DONE, пока обязательные возможности остаются лишь в документах.

**Порядок продолжения:** закончить #216 без потери текущей работы → подтвердить trusted context и требуемые provider роли в #211 → внедрить #218 в существующий train → переподготовить будущие/ещё не допущенные задания по матрице → выполнить критерии приёмки. Подключение второго интерфейса PMA не требует нового runner; его проверка не останавливает действующий пригодный канал. Активные исторические задания не переписываются.
