# GoBadminton CLEAN — Project Record & Handoff Policy

Редакция 2.0, 22.10.2026. Сохранены требования долговременной памяти; устранены прежние зависимости от Hub/внешнего launcher. Полномочия и процесс задаёт [единый регламент](ENGINEERING_OPERATING_MODEL.md).

**Chat is transport. GitHub is durable project record.**

## Что и где хранится

В `anpavel84-afk/gobadminton-clean` сохраняются решения, текущие правила, ADR, спецификации, точные prompts/assignments, handoffs, результаты review и ссылки на evidence. GitHub Issues/Projects — требования, приоритеты и связи; Actions/PR/серверные receipts — факты исполнения. Отдельный ручной реестр не заменяет ни один из этих источников.

Канонические предметные документы — в своих разделах `docs/`/packages. Непринятые материалы — `docs/workbench/` с явным `WORKING DRAFT — NOT APPROVED — NOT CANONICAL`; prompts — `docs/prompts/`; передачи — `docs/handoffs/`. Dated отчёт о фактах не становится правилом из-за публикации в Git.

Бинарные макеты, фотографии, скриншоты и архивы evidence — в разрешённом проектном хранилище `files.anpavel.ru` с контрольной суммой, описанием и разрешённой ссылкой. Использовать существующий проверенный канал загрузки; не предполагать работоспособность старой команды. Не коммитить такие архивы, credentials, сессии или персональные данные. Временный sandbox/чат не может быть единственной копией существенного результата.

## Standing permission и пределы

Участник с действующим доступом и соответствующим scope может сохранить собственный working artifact/handoff в разрешённой ветке CLEAN без нового micro-GO только ради обмена файлами. Это не разрешает менять продукт, чужую работу, действующий канон, workflow, бюджеты, права или PROD. Доступ к Git не равен execution authority.

Нет обязательного внешнего Hub binding для проектного обмена. Внешние role templates могут быть справочными; входы и границы существенного назначения должны быть восстанавливаемы из CLEAN. Owner не используется как постоянный курьер.

## Обязательный prompt / assignment

Указать: получателя/роль; продуктовый результат; exact canonical inputs/base; допустимые файлы и эффекты; non-goals; зависимости; acceptance; проверки и допустимую среду; результат/handoff; rollback, когда применимо. Маршруты моделей и бюджеты оформляются по действующей поддерживаемой схеме, а не произвольным полям.

Рабочий prompt и machine admission — разные вещи. Публикация документа, PR или комментария с планом не создаёт immutable допуск.

## Обязательный handoff

Указать from/to, дату, статус, точный commit правил и source/candidate SHA; что изменено; результаты с exact evidence; что не проверено и почему; актуальные blockers; разрешённый следующий шаг. FACT, OWNER_DECIDED, PROPOSED, QA_PASS, CI_PASS, DEV_ACCEPTED и OWNER_ACCEPTED не смешиваются.

GitHub документ/код связывать immutable commit permalink. Branch URL допустим как навигация, но не как доказательство проверенной ревизии. Проверять существование файла/commit; не фабриковать ссылку, receipt, подпись, membership или независимый PASS.

## Непрерывность и история

Сохранять историю задач, failures, attempts, решений и прежние identifiers как provenance. Не импортировать старую очередь и не переносить её разрешения. Ссылки на архивные доказательства нельзя массово заменить на новый repo slug: такие SHAs могут не существовать в CLEAN.

После значимой работы новый PMA/исполнитель должен продолжить её по CLEAN и разрешённым evidence, без обязательного чтения чата. Недоступный вход обозначать точно; не молча повторять всё исследование и не объявлять отсутствующее выполненным.

Действующие правила меняются через reviewed PR по разделу 11 [регламента](ENGINEERING_OPERATING_MODEL.md); рабочие документы не могут самопровозгласить новый канон.
