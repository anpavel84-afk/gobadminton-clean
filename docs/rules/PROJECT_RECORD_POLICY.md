# GoBadminton CLEAN — Project Record & Handoff Policy

Редакция 2.0, 22.10.2026. Сохранены требования долговременной памяти; устранены прежние зависимости от Hub/внешнего launcher. Полномочия и процесс задаёт [единый регламент](ENGINEERING_OPERATING_MODEL.md).

**Chat is transport. GitHub is durable project record.**

## Что и где хранится

В `anpavel84-afk/gobadminton-clean` сохраняются решения, текущие правила, ADR, спецификации, точные prompts/assignments, handoffs, результаты review и ссылки на evidence. GitHub Issues/Projects — требования, приоритеты и связи; Actions/PR/серверные receipts — факты исполнения. Отдельный ручной реестр не заменяет ни один из этих источников.

Канонические предметные документы — в своих разделах `docs/`/packages. Непринятые материалы — `docs/workbench/` с явным `WORKING DRAFT — NOT APPROVED — NOT CANONICAL`; prompts — `docs/prompts/`; передачи — `docs/handoffs/`. Dated отчёт о фактах не становится правилом из-за публикации в Git.

Бинарные макеты, фотографии, скриншоты и архивы evidence — в разрешённом проектном хранилище `files.anpavel.ru` с контрольной суммой, описанием и разрешённой ссылкой. Использовать существующий проверенный канал загрузки; не предполагать работоспособность старой команды. Не коммитить такие архивы, credentials, сессии или персональные данные. Временный sandbox/чат не может быть единственной копией существенного результата.

**Единственное штатное внешнее место для нетекстовых рабочих артефактов проекта — уже существующий Shared Artifact Hub, не GitHub и не новый сервис.**

| Для Owner / PMA / ссылок в Issue | `https://files.anpavel.ru/projects/gobadminton/` |
| На немецкой VPS `vmi3510488` | `/opt/shared-artifact-hub/data/projects/gobadminton/` |

**Подтверждено 23.10.2026:** существующий PNG `design/map/M2R_mockup.png` доступен по HTTPS (HTTP 200, `image/png`, 2 254 493 байта); SHA-256 файла на диске и скачанного по HTTPS совпадает: `bf53191f8f917a119105ea058a3becefbbb50ca6fc6bf64d8d07d8f5b5cd2b60`. Это подтверждает **публикацию и чтение конкретного файла**, но **не** полномочия PMA на upload и не автоматическую доставку файлов агенту.

**Нормальный путь для макета / скриншота / PDF / ZIP / визуального QA evidence:**

1. **Owner → PMA.** Owner прикладывает исходный макет к PMA (либо даёт URL уже загруженного материала). PMA сам координирует передачу; Owner не должен переносить файл между моделями вручную.
2. **PMA / уполномоченный uploader → Artifact Hub.** Использовать уже имеющийся проверенный способ загрузки через доступную авторизованную веб-сессию или разрешённый серверный инструмент. Класть в `projects/gobadminton/`, предпочтительно `design/<issue-or-topic>/<versioned-name>.<ext>` для входных макетов, сохраняя существующие пути. Не создавать общий доступ на запись, новый upload API, токены или отдельный сервис. При неизвестной/неработающей загрузке отмечать конкретный blocker; наличие HTTPS GET не доказывает upload.
3. **PMA → GitHub Issue / точное assignment.** Записать **URL, относительный путь, SHA-256, размер, версию/назначение, Issue и статус принятия Owner** (когда применимо). Указывать точный файл, а не ссылку только на каталог. GitHub хранит *метаданные и спецификацию*, не копию бинарного макета.
4. **Trusted bridge → task-scoped workspace → автор.** До запуска Cursor/Codex/Antigravity разрешённый исполнитель получает указанный файл существующим подтверждённым способом (локальная копия с VPS или HTTPS), проверяет SHA-256 и предоставляет **read-only вход** в разрешённом task workspace. Модели даются короткий путь/ссылка + задача, а не PNG/PDF/архив, закодированный в prompt. Не подменять файл при том же URL и не передавать непроверенную версию. Если поддерживаемый adapter не умеет подготовить вход или изоляция запрещает доступ — `NOT_CONNECTED`, без ложного `READY` и обхода sandbox.
5. **Автор → QA → PMA.** Автор публикует изменённый исходный код и текстовые контракты через обычный PR; промежуточные PNG/скриншоты/видео/объёмные отчёты публикует в том же Hub с новыми версиями и SHA-256. Независимая QA получает точный candidate SHA и те же immutable input references, публикует короткий verdict/receipt со ссылками. DEV/PROD gates остаются обычными.

**Что НЕ класть в GitHub:** рабочие PSD/Figma exports, PNG/JPEG-макеты, серии браузерных скриншотов, видео, большие PDF, сырые логи, архивы и тяжёлые промежуточные сборки. Исключение — **настоящие используемые приложением source/static assets** (иконки, необходимые изображения, небольшие тестовые fixtures), осознанно включённые в продуктовый build/тесты: они могут оставаться в versioned source по предметному решению. Не вводить глобальный `.gitignore` на PNG/SVG, который сломает приложение.

**Конфиденциальность:** прямые ссылки в публичном Artifact Hub считать потенциально доступными третьим лицам. Туда помещать только материалы, разрешённые к такому доступу. Секреты, персональные данные, внутренние дампы, закрытые QA receipts, токены и private evidence не размещать в публичных каталогах; использовать уже предусмотренное закрытое хранилище и доступы. Не менять права на PROD, настройки чужих проектов или существующие приватные архивы.

**Фактическая граница подключения на 23.10.2026:** сервис и путь проверены; отдельные слоты `/srv/gb-slots/slot1`, `/srv/gb-slots/slot2` имеют разные учётные записи и приватные task worktrees. Автоматическая доставка файла Artifact Hub в Cursor/Antigravity train и upload непосредственно из PMA Work **не подтверждены**; этот текст устанавливает **правильный контракт обмена**, а не объявляет адаптер установленным. Реальное подключение делается только как адресная настройка существующего transport/stage с проверкой file → hash → author → QA, без нового runner и без изменения продолжающейся операции. Не считать принятие документа runtime deployment.

## Standing permission и пределы

Участник с действующим доступом и соответствующим scope может сохранить собственный working artifact/handoff в разрешённой ветке CLEAN без нового micro-GO только ради обмена файлами. Это не разрешает менять продукт, чужую работу, действующий канон, workflow, бюджеты, права или PROD. Доступ к Git не равен execution authority.

Нет обязательного внешнего Hub binding для проектного обмена. Внешние role templates могут быть справочными; входы и границы существенного назначения должны быть восстанавливаемы из CLEAN. Owner не используется как постоянный курьер.

## Обязательный prompt / assignment

Указать: получателя/роль; продуктовый результат; exact canonical inputs/base; допустимые файлы и эффекты; non-goals; зависимости; acceptance; проверки и допустимую среду; результат/handoff; rollback, когда применимо. Маршруты моделей и бюджеты оформляются по действующей поддерживаемой схеме, а не произвольным полям.

Рабочий prompt и machine admission — разные вещи. Публикация документа, PR или комментария с планом не создаёт immutable допуск.

## Обязательный handoff

Указать from/to, дату, статус, точный commit правил и source/candidate SHA; что изменено; результаты с exact evidence; что не проверено и почему; актуальные blockers; разрешённый следующий шаг. FACT, OWNER_DECIDED, PROPOSED, QA_PASS, CI_PASS, DEV_ACCEPTED и OWNER_ACCEPTED не смешиваются.

GitHub документ/код связывать immutable commit permalink. Branch URL допустим как навигация, но не как доказательство проверенной ревизии. Проверять существование файла/commit; не фабриковать ссылку, receipt, подпись, membership или независимый PASS.

## Непрерывность и история

Сохранять историю задач, failures, attempts, решений и прежние identifiers как provenance. Не импортировать старую очередь и не переносить её разрешения. Ссылки на архивные доказательства нельзя массово заменить на новый repo slug: такие SHAs могут не существовать в CLEAN.

После значимой работы новый PMA/исполнитель должен продолжить её по CLEAN и разрешённым evidence, без обязательного чтения чата. Недоступный вход обозначать точно; не молча повторять всё исследование и не объявлять отсутствующее выполненным.

Действующие правила меняются через reviewed PR по разделу 11 [регламента](ENGINEERING_OPERATING_MODEL.md); рабочие документы не могут самопровозгласить новый канон.
