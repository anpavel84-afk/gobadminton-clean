# PMA — применение эталонной архитектуры

Полный нормативный источник — [ENGINEERING_OPERATING_MODEL.md](../../rules/ENGINEERING_OPERATING_MODEL.md). Этот checklist не содержит второй таблицы моделей или дополнительных полномочий.

## Войти или сменить интерфейс

PMA может работать из ChatGPT Work или Grok-бота. Прочитать принятую архитектуру и durable состояние GitHub/Actions/server. Установить свою роль/доступ, актуальные assignments и процессы. Смена чата не является повторным запуском; изменяющие команды сериализуются, а при неподтверждённой общей защите активен один mutating-канал.

## Подготовить задачу

Найти/создать постоянное требование без дубля, сохранить цель/приоритет/связи в существующем Project. Технический PM читает код, отдельно оценивает автора и QA, предлагает этапы, проверенные model IDs/effort и fallback. PMA проверяет по эталону и делегации, не просит micro-GO внутри разрешённого scope.

Зафиксировать accepted rules revision, base, allowed paths/effects, зависимости/locks, acceptance и конечные бюджеты. Admission оформить по поддерживаемому протоколу; обсуждаемому Issue — единственный immutable допускающий объект, без конкурирующего body/comment. Backlog или документ не являются запуском.

## Довести до результата

Сохранить существующий train/ownership. Автор → публикация → детерминированные проверки → независимая QA → обязательные gates/интеграция → DEV ACCEPTED и проверка пользовательского результата. Новый интеграционный SHA проверяется по действующим правилам. Исторические задания не переписывать задним числом ради нового порядка.

**Содержательный FAIL → отдельная Astra High failure_diagnosis → сохранённый repair brief → авторская доработка → новые тесты и независимая QA.** Astra получает exact SHA/findings/логи/контракты и историю. Следующий новый FAIL требует уточнения причины; идентичный пригодный диагноз не оплачивается второй раз. Диагноз не является QA PASS.

При исчерпании пакета применить §6 единого регламента: сохранить историю, использовать готовый диагноз и оформить конечное продолжение в утверждённом scope без нового Owner micro-GO. Стандартные новые продуктовые задания — 3 попытки, далее diagnosed recovery; one-shot не является обычным default. Не сбрасывать counters и не повторять UNKNOWN. Ошибки auth/quota/среды и ожидание CI не выдавать за source FAIL. Локальная остановка не отключает независимую очередь.

При отсутствии Cursor OPS-допуска использовать разрешённый защищённый Codex Sol High для адресного ремонта адаптера и отдельную QA, не новую универсальную систему допусков. Новые квалификационные вызовы после исправлений оформляются по §6, не как replay исчерпанной операции.

Если недоделка обнаружена после DEV, сверить исходные критерии. Невыполненное требование/регрессия идёт в связанную доработку с сохранением evidence; новое пожелание — отдельный scope. Инструмент вместо конечного результата не является DONE.

## Следить за фактической системой

Проверять qualified provider roles, выбранную/effective модель, usage, реально запущенный процесс и свежесть статусов. Документ с нужной стадией не означает реализованный код. Обычные независимые задачи продолжаются при локальном сбое. Не перезапускать весь train вслепую и не подменять watchdog периодическим GPT-чатом.

## Применить эту редакцию

Порядок обновления accepted context — §11 единого регламента; прежняя [инструкция принятия](../../prompts/pma-adopt-engineering-rules-20261022.md) сохраняет историческое происхождение, а не требование повторить PR #217. #216 — уже проведённая безопасная уборка; #211 — доверенный контекст и providers; #218 — реализация Astra FAIL loop. Подключение Grok подтверждается отдельно; не требуется второй runner.

Owner получает короткий результат: принятый нормативный commit; что реально установлено/проверено; достигнутый продуктовый результат; конкретные blockers и следующий разрешённый шаг. PROD — отдельный GO, не следствие документации.
