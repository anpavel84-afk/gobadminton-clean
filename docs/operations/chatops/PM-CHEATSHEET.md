# PMA — рабочий checklist

Полномочия, маршруты и приёмка определяются [единым регламентом](../../rules/ENGINEERING_OPERATING_MODEL.md). Этот checklist его применяет и не создаёт второй набор правил.

## Принять требование

Найти существующий Issue, сохранить продуктовый результат и Owner decision, исключить дубль, связать с существующим GitHub Project. Исторический GB-ID сохранить как reference. Backlog-запись не считать запуском. Свежие приоритеты не брать из локального JSON/старого ACTIVE_BACKLOG.

## Подготовить исполнение

Передать техническому PM задачу и ограниченный кодовый контекст. Получить осмысленный план, зависимости, отдельную оценку сложности автора/QA, exact проверенные model IDs/effort и fallback. Проверить scope и соответствие принятой матрице; не требовать Owner micro-GO внутри существующей делегации.

Сформировать точный допустимый admission по установленной версии протокола. Для обсуждаемого Issue — один неизменяемый Owner admission-комментарий, без параллельного валидного body admission. Рабочий план, новая документация и комментарий Advisor не дают автоматического admission.

В preflight записать rules commit, исходный SHA, права/пути, writer lease и роль. Передать полный канонический текст правил либо подтвердить его загрузку; одного линка недостаточно. Проверить установленные adapter capabilities и допустимый бюджет, не по календарю/подписке.

## Довести до результата

Сохранить ownership существующего train; не запускать ручного второго автора. Следить за реальными фазами, model process, QA, CI и DEV. На сбое читать точный failure; неизвестный результат не дублировать. Продолжать независимые допущенные задачи.

Самопроверку автора, независимую QA exact SHA, CI, DEV ACCEPTED и Owner acceptance учитывать раздельно. После изменения candidate соблюдать действующие fresh gates. Не закрывать продуктовую задачу по одному PR или инструменту без конечного результата.

## Цикл исправления QA/CI FAIL

После содержательного QA/CI FAIL получить exact SHA, findings/логи, прошлые попытки и направить отдельное экспертное заключение **Codex Astra High (failure_diagnosis)** до выдачи очередного авторского задания — по [разделу 8.1 канонического регламента](../../rules/ENGINEERING_OPERATING_MODEL.md). Сохранить один hash-bound repair brief с корневой причиной, минимальным исправлением и regression tests. Автор исправляет; новая независимая QA и CI проверяют новый SHA. Новый содержательный FAIL → Astra уточняет прежний диагноз; тот же неизменённый FAIL не дублирует дорогой вызов.

В текущем train этот обязательный промежуточный этап ещё требует реализации/квалификации: не писать «автоматически работает» только из-за документа, не переписывать действующие immutable admissions. Обычные auth/quota/timeout/preflight отказы не смешивать с source QA FAIL; старые 3/3 и lineage recovery сохранять.

## Управлять отклонениями

Недоступный provider — причина/evidence/remediation; дорогой fallback — явное основание. Не отключать sandbox ради включения маршрута. Реальные provider limits, внутренние caps и task attempts не смешивать. Искусственный дневной cap отменяется только утверждённым OPS изменением с сохранением ledgers.

При 3/3 действовать штатным bounded recovery/преемником, не сбрасывать счётчик и не плодить повторные задачи ради обхода. Вне разрешённого scope — конкретный вопрос/решение Owner, а не общее «нужен GO».

## Отчитаться

Коротко: пользовательский результат; точная стадия; выбранный/effective provider/model/effort; выполненные проверки и evidence; blocker и его владелец; следующий разрешённый шаг. Никогда не писать RUNNING из факта dispatch или READY из CLI help.

Для правил этой ревизии выполнить [отдельную инструкцию принятия](../../prompts/pma-adopt-engineering-rules-20261022.md); она не разрешает менять активные admissions, контроллер или PROD.
