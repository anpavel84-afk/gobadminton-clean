# Компактный TEST PLAN и инструкции ролей

**Проект.** Применяется после принятия версии основного `PROPORTIONATE_TESTING_PROTOCOL_V1.md` и проверки совместимости с установленным Train. Не новый machine admission. Полный документ не включать в каждый модельный вызов; сохранить immutable reference через существующий Context Exchange.

## Карточка в постановке задачи

```text
TEST PLAN v1
Профиль / причина: T0–T3; эффекты, зависимости, риск.
Доказать: исходные критерии и затронутые инварианты.
Локальный цикл: группы/test IDs; где выполняются.
Финальные проверки: подсистема, независимая QA, нужный CI/DEV/visual/OPS.
Полный набор: где нужен и почему; нет автоматического локального повтора.
Среда: данные, инструменты, fixtures, Git objects; кто закрывает NOT_TESTED.
Повтор/reuse: identity и изменения, требующие новых доказательств.
Бюджет: целевое время и объём сводки; превышение не даёт PASS.
```

Команды берутся из доверенного существующего каталога, а не исполняются как произвольный текст карточки. Перед приёмкой план сверяется с реальным diff.

## Автор: короткая инструкция

Реализуй исходные требования в allowed scope. Выполняй TEST PLAN, не запускай весь проект автоматически после каждой правки. Для bugfix добавь reproducer/regression и проверь адресный набор с затронутыми потребителями. При локальном FAIL исправь причину, а не запускай тот же полный suite на неизменённом кандидате.

Не снижай риск, не удаляй assertions и не скрывай ошибки/skip. Маленькая правка прав, приватности, учёта расходов или PASS-парсера не становится безопасной из-за размера. Отсутствующую среду обозначь NOT_TESTED и используй назначенный runner. Непроверенное не называй PASS.

Повтор полного прогона требует изменившегося релевантного входа или конкретного основания. Передай exact candidate, короткий итог, новые/сохранённые findings, результаты и ссылки на полные логи. Не объявляй собственную работу независимой QA. Полномочия, лимиты, UNKNOWN, продуктовая пауза и PROD остаются по действующим правилам.

## Независимая QA: короткая инструкция

Проверь exact diff и текущие критерии; оцени полноту TEST PLAN, влияние зависимостей и качество тестов. Не начинай полный аудит неизменённой системы. Используй подлинное подходящее exact-version CI evidence, а не одну авторскую фразу «всё прошло».

Выполни независимые адресные repro/негативные проверки там, где это даёт дополнительную гарантию. Расширяй набор по обнаруженному риску с коротким основанием. Не повторяй весь baseline для уже известных ошибок той же среды.

NOT_TESTED — открытое обязательство, не дефект кода и не PASS. Сохраняй существенные прежние findings. Для UI нужны применимые реальные функциональные и визуальные доказательства; для T3 — проверка затронутой границы доверия. Независимость, provenance, действующие CI/DEV gates и запрет на самопринятие сохраняются. Новый SHA требует адресного review или доказанного существующим механизмом reuse, а не ручной подмены verdict.

## PMA / интегратор: короткая инструкция

При постановке назначь риск и конкретный test plan; для типовой задачи используй шаблон без нового LLM-planner. Сопоставь каждый обязательный критерий с проверкой и средой. Перед финалом проверь реальную область diff; не доверяй слову автора «micro».

Полный CI первой стадии не сокращай. Не запускай одинаковые тяжёлые группы параллельно на том же fingerprint. Не расходуй модельные вызовы на polling; существующий runner собирает результат, модель получает короткую сводку и нужный фрагмент FAIL. Полные логи сохраняются без секретов.

Отделяй source QA, исполненные тесты, UI evidence, интеграционную версию и live DEV. Ошибки среды закрывай в подходящем runner; совпавшие ошибки base/head не означают полного PASS. Переиспользуй только проверяемые receipts в допустимой области. Выполняй root/OPS исключительно штатным доверенным способом. Не возобновляй продуктовую очередь и не расширяй расходы или права этим регламентом.
