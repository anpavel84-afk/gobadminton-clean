Workers используют full либо квалифицированный common+role capsule **из той же принятой редакции**, затем exact assignment и применимые предметные inputs. Ссылка не доказывает загрузки. До подтверждения доступности полного канона фактической identity — полный fallback. Candidate не может изменить правила собственной QA.

В preflight фиксировать repo, rules commit/hash, роль, source/base/candidate SHA, assignment/admission, allowed paths/effects, writer ownership и requested/effective route. Семейства моделей — §5 канона, детальная role × risk матрица и классы FAIL — SMART_ROUTING.md, полномочия в §3, попытки и продолжение в §6, FAIL-цикл в §8.1. Здесь нет второй таблицы моделей. Astra — read-only эксперт по классу (не автор и не обычная QA); пока классификатор не установлен, контроллер применяет прежний маршрут Astra перед ремонтом, и обходить его по собственной оценке «простоты» нельзя.

### Корректная постановка инструментальных операций и платформенные отказы

1. **Сначала правильная операция, затем инструмент.** Перед вызовом определить конкретную инженерную цель, минимально необходимые полномочия, файлы и ожидаемые эффекты. Не объединять обычную разработку, секреты, root-операции и посторонние действия без необходимости.
2. **Платформенный отказ не равен блокировке всей задачи.** При `blocked by OpenAI's safety checks` установить, не был ли выбран неправильный тип операции или избыточный объём доступа. Нераскрытую причину не выдавать за установленный диагноз.
3. **Выбирать стандартный разрешённый процесс.** Исходники — exact Git commit/SHA; тесты — синтетические fixtures и CI; независимая QA — точный изолированный candidate; OPS — существующий авторизованный механизм с backup/rollback. Не читать настоящие секреты, когда достаточно синтетических данных.
4. **Не обходить защиту.** Не маскировать, кодировать или переформулировать запрещённое действие ради прохождения фильтра; не менять identity или канал для его повторного выполнения. Допустима только действительно другая правомерная операция с минимальными полномочиями.
5. **Классифицировать ошибки отдельно.** OpenAI safety refusal, GitHub HTTP 403, AppArmor EACCES, ошибка теста и отказ модели — разные причины, не один общий BLOCKED.
6. **Продолжать работу.** Сохранить точную операцию, параметры без секретов и полный доступный отказ; выбрать существующий разрешённый процесс. Если необходимая операция недоступна, блокировать только затронутый этап и продолжать независимые разрешённые задачи. Не изобретать способ обхода.
7. **Не повторять известные неудачные запросы без изменения условий.** Учитывать прежние отказы до следующего инструментального вызова. Новое название ветки, обёртки или инструмента само по себе не является изменением условий.

**Главный принцип: корректно проектировать разрешённую операцию, а не искать способ провести запрещённую.** Основание — прямое Owner Addendum 24.10.2026; оно не расширяет права или исключения из §7 полного канона.

## Owner addendum · Lean DEV acceptance · 27.10.2026

Прямое решение Owner применяется **только к новым обычным продуктовым admissions** и в этой области заменяет прежний обязательный Astra FAIL-маршрут выше, §8.1 EOM / SMART_ROUTING и прежний лимит авторских проходов. Cursor Auto — автор по умолчанию, если Owner заранее не выбрал другого доступного исполнителя; максимум **три авторских прохода всего** (первая реализация + до двух исправлений). Независимый модельный QA по умолчанию один: квалифицированный Antigravity либо Codex Sol Medium. Два модельных review каждой обычной задачи не требуются.

Для известных обычных ошибок тестов и замечаний QA передавать автору точные findings и лог непосредственно, без отдельного Astra-вызова. В новых обычных admissions **не добавлять необязательное `failure_diagnosis`**; установленный валидатор уже поддерживает его отсутствие. После ремонта проверять изменённый код и связанные риски, без полного повторного аудита неизменённых компонентов. Этот порядок **не распространяется** на полномочия, секреты, конкурентный доступ, привилегированные установщики и другие подтверждённо критические изменения: для них сохраняется подходящий независимый review.

Обязательные CI, DEV smoke, пользовательские критерии и серверный **DEV ACCEPTED** сохраняются. Merge и ответ CLI не доказывают приёмку. Старые admissions, attempts и UNKNOWN не редактировать и не переигрывать. Квота Antigravity: до пяти вызовов на GitHub Issue за календарные сутки (UTC в действующем учёте), суммарно по ролям, без общего дневного потолка; исторические расходы и старые immutable-пакеты сохраняются.

Использовать существующие назначения и механизмы; не создавать classifier, scheduler или framework ради этого решения. Публикация этого addendum не меняет root pinned-файлы, installed controller или активную установку. Успешная квалификационная #346 не доказывает общий маршрут: отдельно подтвердить следующую обычную продуктовую задачу с Antigravity QA и указать оставшуюся ручную привязку к Issue/исполнительной среде.

## Owner OD-014 / OD-014A · Git-based installation · 28.10.2026

Для текущего #360 и последующих установок через его V5-путь содержимое задаёт принятый Git commit SHA и точные Git blobs. Установочный checkout должен быть чистым; установленные целевые файлы сверяются с этими blobs. Заранее зашитые пофайловые SHA старой установки, старые marker/inventory hashes и legacy manifest digest не являются условием разрешения обновления. Текущее содержимое и метаданные сохраняются как фактический backup для rollback; это не подтверждение соответствия историческому pin.

`always True` / pass-through не подтверждают целостность. Сохраняются Linux root:root, допустимые типы файлов, защита от опасных symlink, существующий install lock, атомарная замена, фактическая проверка нового содержимого и rollback. Упрощение адресное: незатронутые контракты, sandbox, полномочия, бюджеты, история и UNKNOWN не отключаются и не сбрасываются. Отдельная массовая миграция TEST PLAN / PINS в #360 не выполняется. Отсутствие исторического pin не является QA FAIL по новому контракту. READY подтверждается реальной принятой Antigravity QA после установки, а не ручной записью статуса.
