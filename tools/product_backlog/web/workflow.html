РЕГЛАМЕНТ OWNER · PM · ДИЗАЙН · РАЗРАБОТКА · QA · РЕЛИЗ

Одна просьба.
Один постоянный номер.

GitHub хранит обязательства продукта. Монитор показывает, что попросили, что опубликовано и что действительно приняли. Runner выполняет технические задания, но не определяет, что Owner уже получил.

Главное правило

Записать → принять в работу → реализовать → проверить → опубликовать → получить решение Owner.
Ни merge, ни зелёная QA, ни запуск контейнера не заменяют последнюю проверку. Новая просьба не является разрешением на автоматический запуск.

Продуктовый источник правды: registry.json в GitHub main. Подробный регламент, роли и команды для PM доступны в репозитории.

Что делает PM с каждой просьбой

  1. Ищет существующий номер. По экрану, смыслу, старому Feedback ID и техническим ссылкам. Уточнение обложки — дополнение GB-020, а не новая несвязанная карточка.
  2. Сохраняет просьбу. Понятное название, источник, проверяемый результат, ответственный и следующий шаг. После успешного GitHub сохранения сообщает GB-номер. Черновик в чате не считается сохранением.
  3. Определяет объём и ограничения. Где нужен дизайн, архитектура, API, приватность или решение Owner. Отложенное не удаляет. Запись не запускает Runner.
  4. Связывает выполнение. В Implementation/QA/релизе указывает тот же GB. Один технический пакет может обслуживать несколько продуктовых задач; это не закрывает их автоматически.
  5. Проверяет реальную публикацию. Среда, URL, Web/API SHA, дата и доказательство. Код установлен, но Radar выключен — так и записывается.
  6. Возвращает результат Owner. Что открыть и что проверить. «Принимаю» сохраняется с источником. «Не работает» возвращает эту же карточку в работу с новой записью истории.

Три независимые колонки

КолонкаЧто доказываетЧто не доказывает
Код / QAЕсть исходник, кандидат, независимое заключение, merge.Что функция уже доступна в браузере.
ПубликацияКонкретный образ / версия установлен в конкретной среде; известны ограничения.Что выключенный флаг включён или сценарий работает под аккаунтом.
Приёмка OwnerOwner явно принял результат на указанной версии.Что все остальные задачи того же релиза тоже приняты.

«Ждёт проверки Owner» не означает «плохо сделано». «На сайте» не означает «готово всё». Ноль подтверждённых задач означает, что явная приёмка ещё не записана.

Статусы на человеческом языке

Зафиксировано → Принято в бэклог → В очереди → В разработке → На независимой QA → Готово к публикации → Публикуется → Опубликовано → Ждёт проверки Owner → Принято Owner.

Нужна проверка — восстановлена историческая просьба, но её исполнение не доказано. Заблокировано — указаны конкретная причина, следующая роль и действие. Отложено — не текущий релиз, но номер сохранён. Объединено — ссылка на основную карточку; старая не исчезает. Отменено Owner — только явное решение с источником.

Пример: обложка профиля

GB-020 · Загрузить и менять свою фотографию обложки профиля — это отдельное изображение, не аватар и не обложка игры. Если в релизе появился только AvatarEditor, GB-020 остаётся незавершённой.

Реализация связывает UI загрузки, storage/API и сохранение. QA проверяет замену, удаление, права и отображение. Release записывает версию. Owner меняет обложку в своём аккаунте и принимает — только тогда карточка закрыта.

Как сохранить изменение без потери истории

Команда обновления использует фактически прочитанную ревизию. Параллельная запись, удаление номера, подмена истории и самоприёмка отклоняются. Не редактировать сгенерированную копию на сервере.

python3 -B tools/product_backlog/manage.py --check
python3 -B tools/product_backlog/manage.py \
  --patch /tmp/product-change.json --role pm \
  --evidence 'точный источник решения' \
  --reason 'что изменилось и почему' \
  --expected-revision ФАКТИЧЕСКАЯ_РЕВИЗИЯ

После проверки: сохранить в Git, сверить свежий main, опубликовать без force-push. Если ревизия поменялась, пересобрать изменение поверх свежего реестра. Поле github_published=false означает только локальное изменение.

В браузере «Зафиксировать просьбу» готовит Issue или текст для PM. Эта кнопка не имитирует сохранение: запись появляется после реальной публикации Issue и регистрации PM.

Ничего не исчезает

Запрещены удаление зарегистрированных карточек и повторное использование номера. Исправление формулировки, перенос релиза, отказ QA, объединение и регрессия имеют отдельное событие с причиной и источником. История защищена цепочкой контрольных сумм, а прежние полные версии остаются в Git.

Реестр читает небольшой программный синхронизатор примерно раз в минуту. При ошибке сети или данных сохраняется последняя валидная копия. Возраст и Git SHA показаны сверху. Мониторинг не вызывает Codex и не записывает в очередь Runner.

Что восстановлено и чего нельзя обещать

Начальная загрузка включает 102 пункта сверки адвайзера, отдельное сопоставление всех 17 замечаний Feedback Manager, дополнительные известные просьбы Owner и весь архив 551 технического задания. Технические связи по ключевым словам — только подсказки для PM, не доказательства готовности. Неопределённые записи сохранены в GB-135.

Не заявляется доступ ко всем сообщениям всех чатов. Позднее обнаруженная просьба получает новый номер или присоединяется к существующему с новым источником. Future/исторические идеи не превращаются молча в обязательства ближайшего релиза.

Реестр требований ≠ оперативная очередь. Публикация ≠ приёмка Owner.
